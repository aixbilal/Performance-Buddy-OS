# Human Control Principle

## Purpose

Define control, consent, and authority requirements for deterministic, automated, and AI-assisted interactions.

## Control model

The user initiates or authorizes meaningful change. CORE validates rules and permissions. Background work executes only registered approved behavior. AI proposes and explains; it does not silently commit consequential writes.

## Interaction classes

| Class | Examples | Control requirement |
|---|---|---|
| Read/view | Open record, search | Permission and clear provenance |
| Low-risk reversible write | Toggle routine, edit draft | Immediate feedback and undo where feasible |
| Consequential write | Marks, plan reallocation, delete, permission | Preview and explicit confirmation/approval |
| AI-proposed write | Move schedule, change tracker | Before/after, reason, validation, explicit approval |
| Background action | Backup, indexing, timer | Prior configuration, status, pause/retry/recovery |

## Consent rules

Consent is specific: enabling sync does not enable AI provider access. Permission changes show affected data and features. Bundled or preselected consent is prohibited for sensitive or remote processing.

## Automation

Users can inspect, pause, disable, and understand automations. The system records actor, time, reason, and outcome. Automation cannot override protected constraints or domain invariants.

## Failure safety

Timeout, model failure, or ambiguous intent leaves confirmed data unchanged. When control cannot be safely preserved, the system blocks and explains rather than guessing.

## Acceptance criteria

Every meaningful mutation has an attributable path; approval cannot be bypassed through palette, mobile, background, or AI surfaces; and revocation takes effect predictably.
