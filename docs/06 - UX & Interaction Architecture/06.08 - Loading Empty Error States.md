# Loading Empty Error States

## Purpose

Define truthful, actionable states for waiting, absence, insufficient evidence, permission limits, and failure.

## Loading

Show loading only for work that is actually pending. Preserve existing content during refresh when safe. Indicate scope—local database, index, integration, sync, or AI—so an optional outage does not appear global. Offer cancel for long user-initiated work where feasible.

## Empty states

Distinguish:

- no records yet;
- no results for filters/search;
- insufficient evidence;
- not permitted/private;
- index not built or stale;
- optional service offline;
- data unavailable due to error.

Each state explains the condition and offers a relevant safe action. Do not invent sample records in real data views.

## Errors

Error messages state what failed, what was preserved, user impact, and the next safe step. Validation appears near fields plus a summary when needed. Technical detail can expand for diagnostics without exposing secrets or private data.

## Partial failure

Keep unaffected CORE areas usable. Batch/import/sync operations report per-item outcomes and never label a partial result as complete. Retry must be idempotent or explain duplication risk.

## Tone and accessibility

Avoid blame. Move focus to an appropriate error summary, announce asynchronous errors accessibly, and preserve entered data.

## Acceptance criteria

Every state is distinguishable without color alone, optional failures are contained, and users know whether data was saved and how to recover.
