# Attachment Handling

## Purpose

Index attachment metadata and approved extractable content safely without executing or duplicating user files.

## Supported contract

Each attachment reference stores vault-relative path, canonical resolved path, media/MIME type, size, checksum, modification marker, parent-note links, permission state, extraction status, and diagnostics. Exact supported formats and limits are implementation configuration.

## Rules

- Type detection uses content and extension checks; mismatches are flagged.
- Files are never executed, and active content is not rendered unsafely.
- Large, encrypted, corrupt, unsupported, or password-protected files remain metadata-only with status.
- Extracted text is a derived local projection linked to page/position where possible.
- OCR is optional and its output is labeled unverified.
- Duplicate checksums may suggest references but never delete files.

## Privacy

Attachment permissions may be stricter than the parent note. Remote OCR or model processing requires explicit task-scoped consent.

## Acceptance criteria

Unsafe and oversized files are contained, metadata search still works, extraction failures do not block other files, and source attachments remain unchanged.
