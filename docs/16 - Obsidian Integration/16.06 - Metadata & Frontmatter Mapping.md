# Metadata & Frontmatter Mapping

## Purpose

Map selected YAML frontmatter and Obsidian metadata to Knowledge OS references without treating arbitrary keys as canonical domain facts.

## Mapping contract

Each configured key maps to a target field, type, normalization rule, precedence, privacy effect, and write policy. Candidate keys may include title, aliases, tags, course reference, topic references, source, created/updated dates, and status.

## Rules

- Unknown keys are preserved in source and ignored or indexed generically.
- Mapping is versioned; remapping rebuilds projections, not note content.
- Course or topic strings create candidate matches requiring deterministic resolution or review.
- YAML dates, booleans, arrays, and strings are parsed without locale guessing.
- Frontmatter never overrides official academic records.
- Duplicate keys, invalid YAML, and type conflicts create file-level diagnostics.

## Write boundary

Baseline mapping is read-only. Any future metadata write must preserve comments/order where feasible, preview changes, and obtain approval.

## Acceptance criteria

Mappings are explicit and reversible, malformed metadata cannot fabricate links, and users can inspect why a field was mapped or ignored.
