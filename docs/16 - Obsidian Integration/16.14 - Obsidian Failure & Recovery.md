# Obsidian Failure & Recovery

## Purpose

Define safe degraded behavior for unavailable vaults, moved/deleted files, parse failures, corrupt indexes, permission errors, concurrent edits, and interrupted background work.

## Failure states

`Vault Missing`, `Access Denied`, `Reference Broken`, `Parse Failed`, `Index Stale`, `Index Corrupt`, `Embedding Unavailable`, `Conflict`, and `Recovery Running` are explicit states with affected scope and last reliable checkpoint.

## Recovery rules

Never recreate or overwrite a missing file automatically. Offer reconnect or rematch candidates with preview. Quarantine corrupt projections and rebuild from permitted sources. Resume idempotent jobs from checkpoints. If a file changes during read/write preparation, discard the candidate and retry or request review.

## Data protection

Raw notes remain untouched by index recovery. Any future write recovery uses backups, atomic operations, and user-visible diffs. Diagnostics minimize paths and content. Disabling integration removes projections according to retention choice without deleting the vault.

## Acceptance criteria

Each failure is contained, clearly reported, and recoverable where possible; no degraded state presents stale content as current; and recovery never broadens permission or modifies sources silently.
