# Incremental Reindexing

## Purpose

Update indexes efficiently after file or permission changes while producing the same result as a full rebuild for the same source state and versions.

## Change pipeline

Receive a candidate change; debounce/coalesce; canonicalize path; re-check scope and permission; fingerprint the file; classify create/modify/move/delete/permission change; parse affected content; update references and index entries transactionally; record checkpoint and diagnostics.

## Rules

- Stable file identity is attempted through configured filesystem signals and checksum, but uncertain moves remain candidates.
- Duplicate events are idempotent.
- Failed parsing retains the prior entry as visibly stale or removes it according to privacy risk.
- Permission restriction purges content immediately rather than waiting for normal indexing.
- A queue overflow or missed-event signal schedules a bounded reconciliation scan.

## Acceptance criteria

Incremental and full indexes compare equivalently in fixtures, retries cannot duplicate entries, interruptions resume from safe checkpoints, and no source file is changed.
