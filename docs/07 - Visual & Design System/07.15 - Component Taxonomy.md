# Component Taxonomy

## Purpose

Define component families, ownership layers, and composition rules without selecting a UI library.

## Layers

| Layer | Examples | Ownership |
|---|---|---|
| Primitive | text, icon, divider, surface | Design system |
| Control | button, field, select, toggle, menu | Design system + UX |
| Feedback | alert, toast, progress, status | Design system + UX |
| Navigation | nav item, breadcrumb, tabs, palette | Phase 05/06 + design system |
| Data | table, list, chart frame, metric | Design system + Analytics |
| Composite | entity header, filter bar, approval card | Shared pattern owner |
| Domain | marks editor, workout load, prayer checks | Domain owner using shared components |
| Shell | desktop/mobile application frame | Platform + design system |

## Rules

Primitives and controls are domain-neutral. Domain components may specialize semantics but must not fork base accessibility or tokens. Composition is preferred over huge components with many mode flags. Variants are named by semantic purpose, not color or screen.

## Required states

Default, hover where applicable, focus, active/pressed, selected, disabled, read-only, loading, validation error, system error, pending, and success. Not every component exposes every state, but omission is deliberate.

## API/documentation requirements

Each component documents purpose, anatomy, variants, content, keyboard behavior, accessibility semantics, tokens, responsive behavior, loading/error/empty states, and prohibited use. UI library selection remains Phase 44 research.

## Acceptance criteria

Components can implement Phase 05–06 patterns without domain leakage, inaccessible custom forks, raw token values, or duplicated semantic ownership.
