# Design Tokens

## Purpose

Define token naming, tiers, governance, modes, and delivery expectations for a platform-independent design system.

## Token tiers

1. **Foundation:** raw scales such as neutral palette steps, spacing, type sizes.
2. **Semantic:** purpose tokens such as text primary, danger border, focus ring.
3. **Component:** limited aliases for component anatomy where semantic tokens are insufficient.

Product components consume semantic/component tokens, not foundation values directly.

## Families

`color`, `type`, `space`, `size`, `grid`, `radius`, `border`, `shadow`, `opacity`, `motion`, `z`, and `breakpoint`. Modes may include dark, future light, high-contrast/system, compact density, and reduced motion.

## Naming

Names describe purpose and state: `color.text.primary`, `color.action.primary.hover`, `space.component.gap`, `motion.duration.feedback`. Avoid names tied to hue, page, or implementation unless the token is truly foundational.

## Governance

Every token has description, type, allowed values/reference, mode behavior, usage examples, and deprecation status. Changes include impact review and visual regression testing. Component-level exceptions must not become hidden global tokens.

## Delivery

Source format and transformation tooling are `RESEARCH REQUIRED`. Outputs must support the selected desktop/mobile stacks, remain usable offline, and preserve semantic names. Generated files are not manually edited.

## Acceptance criteria

No unexplained raw values occur in audited product components, modes resolve completely, token references have no cycles, and deprecated tokens have a migration path.
