# Design Acceptance Criteria

## Purpose

Define the review gates required before a visual pattern or component is considered ready for implementation or release.

## Review gates

### Product and ownership

- Supports a documented user job and canonical domain owner.
- Does not imply future capability is current.
- Distinguishes confirmed, derived, projected, inferred, and AI-proposed content.

### Structure and interaction

- Matches Phase 05 hierarchy and Phase 06 behavior.
- Primary/secondary actions, confirmation, undo, error, and recovery are clear.
- Loading, empty, sparse, long, permission-denied, offline, stale, and failure states exist.

### Accessibility

- Keyboard, focus, semantics, contrast, zoom/text scaling, reduced motion, target size, and nonvisual chart alternatives pass the approved test plan.
- No color-, hover-, drag-, audio-, or motion-only requirement.

### System consistency

- Uses approved tokens and components.
- Responsive behavior covers supported window/content ranges.
- Icons, type, spacing, surfaces, charts, and motion follow their owner documents.

### Privacy and performance

- Sensitive content exposure is reviewed.
- Offline assets and optional-service states work.
- Rendering, animation, large datasets, and target hardware meet budgets once Phase 41 locks them.

## Evidence

Provide annotated design, component/state inventory, token mapping, keyboard/accessibility notes, responsive examples, and review findings. Reference similarity alone is not acceptance.

## Status

Exact accessibility standard version, libraries, fonts, and raw palette remain `RESEARCH REQUIRED`; their absence does not permit skipping functional accessibility checks.

## Final criterion

A design is ready only when it is understandable, buildable, testable, consistent, recoverable, and honest about authority—not merely visually attractive.
