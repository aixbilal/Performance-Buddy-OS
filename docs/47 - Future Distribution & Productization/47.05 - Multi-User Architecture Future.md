# Multi-User Architecture Future

## Status

Multi-user architecture is `FUTURE` and unselected. This document states questions and gates; it does not prescribe a database, cloud, tenancy model, service topology, or framework.

## Required design decisions

A promoted design must define principals and tenant boundaries; resource ownership and sharing; authentication versus authorization; policy enforcement points; local and remote authority; encryption and key ownership; synchronization and conflict semantics; search, cache, vector, log, backup, export, and deletion isolation; audit and support access; quotas and abuse controls; regional and retention requirements; migrations; observability; incident response; and service exit.

Default-deny authorization applies at trusted application and data boundaries. UI filtering, prompt instructions, or client-supplied tenant identifiers are not isolation. Background jobs, retries, analytics, AI retrieval, administrative tools, and recovery paths enforce the same ownership rules as interactive requests.

## Architecture process

Phase 44 must compare alternatives, including remaining single-user or distributing local-only software. Prototypes use synthetic tenants and exercise hostile identifiers, concurrency, stale authorization, backup restore, deletion, and provider failure. An approved ADR records trade-offs and migration consequences.

CORE schemas and services must not absorb multi-user complexity before promotion unless a current single-user invariant independently requires the same design.

## Acceptance criteria

- The architecture has one explicit authority model and testable isolation contract.
- All storage and execution paths enforce ownership consistently.
- Local data portability and an exit path are preserved.
- No implementation begins until research, threat review, migration design, and promotion are approved.
