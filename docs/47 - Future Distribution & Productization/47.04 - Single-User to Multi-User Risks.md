# Single-User to Multi-User Risks

## Principle

Multi-user operation is a change in trust, data ownership, operations, and product responsibility—not a user-ID column added to a personal database.

## Primary risks

- **Isolation:** cross-user reads, writes, search, embeddings, caches, logs, exports, backups, and AI context leakage.
- **Identity and authorization:** impersonation, stale sessions, recovery abuse, shared-device ambiguity, and confused-deputy behavior.
- **Ownership:** unclear control of shared goals, notes, records, recommendations, deletions, and derived analytics.
- **Concurrency:** conflicts, duplicate actions, ordering, partial writes, and differing device state.
- **Privacy and consent:** one person exposing another's data or using it beyond the agreed purpose.
- **AI behavior:** context mixing, memory contamination, unauthorized tools, and recommendations based on another user.
- **Operations:** abuse response, support access, incident notification, retention, deletion, legal requests, and service availability.
- **Migration:** incorrect ownership assignment and irreversible mixing of legacy personal data.

## Required response

Before promotion, produce data-flow and threat models, tenant-isolation tests, authorization rules, shared-resource semantics, audit and support boundaries, deletion/export behavior, migration rehearsals, cost analysis, and rollback or exit plans. Synthetic adversarial fixtures must test cross-user leakage at every boundary.

## Acceptance criteria

- Risks cover data, identity, AI, synchronization, operations, and migration.
- No single-user shortcut is assumed safe under multiple principals.
- Critical isolation or ownership ambiguity blocks promotion.
- Multi-user readiness is established by evidence, not schema appearance.
