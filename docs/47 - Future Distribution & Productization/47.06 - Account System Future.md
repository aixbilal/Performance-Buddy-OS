# Account System Future

## Boundary

CORE does not require an online account. Local application locking, operating-system identity, device enrollment, cloud authentication, and domain authorization are distinct concerns and must not be collapsed into one mechanism.

## Future requirements

If promoted, an account system must define identifiers, verification, authentication protocols, passkeys or multi-factor options, session and refresh-token handling, device enrollment, reauthentication, credential changes, revocation, recovery, lockout, abuse prevention, deletion, export, privacy-preserving audit, and support limits. Authentication proves a principal or session; authorization still validates purpose, resource, operation, data zone, and approval.

Use established protocols and vetted libraries. Do not design custom password storage, token formats, or cryptography. Email/phone use, identity provider choice, recovery proof, age or jurisdiction requirements, token lifetimes, and support access remain `RESEARCH REQUIRED` until an approved decision.

Offline cached sessions need explicit expiry and degraded behavior. Signing out, losing connectivity, or disabling sync must not silently erase valid local records. Account deletion must distinguish remote deletion, local retention, backups, legal limits, and irreversible effects.

## Acceptance criteria

- Account creation is absent from CORE and optional cloud remains reversible.
- Threat tests cover enumeration, replay, fixation, theft, recovery abuse, and revoked devices.
- Authentication cannot substitute for resource authorization or action approval.
- Recovery and deletion behavior is understandable, testable, and honest about limits.
