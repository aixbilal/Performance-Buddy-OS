# Capability & Version Labels

## Purpose

Define the exact product capability labels and prevent future intelligence or platform features from being represented as current CORE behavior.
## Canonical labels

| Label | Meaning | Boundary |
|---|---|---|
| `CORE` | Deterministic, offline product functionality | Must work without an LLM or cloud |
| `LOCAL` | Private on-device AI where feasible | Model-dependent but not cloud-dependent |
| `V1` | Reactive Smart Assistant | Meaningful writes require approval |
| `V2` | Adaptive Coach | Historical analysis and explainable proposals |
| `V3` | Personal Performance Intelligence | Cross-domain and long-horizon reasoning |
| `CLOUD` | Optional remote services and sync | Never required for CORE |
| `MOBILE` | Future companion/capture capabilities | Not the initial command center |
| `FUTURE` | Deferred or experimental scope | Not a commitment |

## Ordering and inheritance

Use `CORE → LOCAL → V1 → V2 → V3` for increasing intelligence. `CLOUD` and `MOBILE` describe deployment/surface dimensions, and `FUTURE` describes commitment state. A feature can carry multiple dimensions, for example `V2 + CLOUD`, but each must be justified.

## Version discipline

Documentation baseline versions (`v1.0`, `v1.x`, `v2.0`) are distinct from capability labels. Product release versions are also separate and will be owned by Phase 42. Never call V1 a software release number.

## Non-negotiable boundaries

Later levels may recommend but cannot bypass deterministic validation, permissions, protected constraints, or human approval. LLMs do not calculate official academic results. Future capability examples must be visibly labeled and cannot appear in CORE acceptance criteria.

## Acceptance criteria

Every feature statement makes its availability clear; no cloud dependency hides inside CORE; and readers can distinguish documentation, release, and intelligence versions.
