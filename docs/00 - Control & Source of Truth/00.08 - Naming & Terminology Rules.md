# Naming & Terminology Rules

## Purpose

Control project, path, identifier, capability, and user-facing terminology to prevent silent conceptual drift.
## Project and path naming

Use **Performance Buddy OS** in current prose and `Performance-Buddy-OS` when a hyphenated root identifier is needed. The locked folder and filenames are exact, including spaces, punctuation, capitalization, and numbering. Historical “Personal Performance OS” wording is allowed only as historical identification.

## Document naming

Numbered files use `PP.DD - Descriptive Title.md`, where `PP` is the phase and `DD` is the two-digit document sequence. Phase READMEs remain `README.md`. Do not add suffixes such as “final”, “new”, or “updated”; lifecycle belongs in metadata.

## Product terminology

- Use Goal → System → Action in that order.
- Use “recommendation” or “proposal” for AI output, not “decision,” when the human remains responsible.
- Use “terminal examination” only where the academic context requires it; otherwise “final examination” may be clearer.
- Use `SGPA/CGPA` precisely and only under authoritative formula definitions.
- Use “mobile companion,” not “mobile replacement,” for planned MOBILE scope.
- Use “optional cloud,” never wording that implies CORE requires an account.

## Identifiers and labels

Capability labels are uppercase. Stable entity identifiers must not embed mutable display names. Dates in metadata use ISO `YYYY-MM-DD`. Decision, risk, assumption, dependency, question, and non-goal registers use IDs such as `DEC-001`, `RSK-001`, and `ASM-001`.

## Enforcement

Terminology changes require glossary impact review. Renaming a locked path requires an approved baseline revision; redirects or migration notes do not substitute for approval.
