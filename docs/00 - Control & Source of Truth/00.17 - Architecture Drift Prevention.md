# Architecture Drift Prevention

## Purpose

Provide detectable guardrails against gradual departure from the approved product principles, scope, ownership, and capability staging.
## Drift indicators

- CORE requires login, internet, or a remote model.
- A future capability is described as already delivered.
- An LLM owns calculations, constraints, or final authority.
- Meaningful writes occur without approval.
- Mobile becomes the primary command center without revision.
- Obsidian is silently replaced.
- Money is folded into a moralized performance score.
- Protected sleep or health constraints become ordinary trade-offs.
- A generic multi-user SaaS model appears in current architecture.
- Multiple documents redefine one rule.
- Unapproved technology names appear as locked choices.

## Prevention controls

Every feature specification declares capability labels, offline behavior, owner, authority, and human-control boundary. Reviews compare changes against the blueprint, Phase 00 decisions/non-goals, and owner documents. CI or documentation checks should later validate paths, labels, metadata, links, and prohibited wording patterns, while human review handles semantic drift.

## Response

When drift is detected: stop dependent approval, identify the governing rule, classify the discrepancy, correct the lower-authority artifact, record material corrections, and revalidate dependents. If the old architecture is intentionally changing, submit a revision instead of editing the baseline silently.

## Acceptance criteria

Drift is visible before implementation commitment; corrections preserve history; and contributors can explain why a proposal fits the current capability and personal-first boundary.
