# Dependencies Register

## Purpose

Make prerequisite knowledge, sources, decisions, and components visible without prematurely locking implementation technologies.
## Dependency types

Dependencies are `DOCUMENT`, `SOURCE`, `DATA`, `DECISION`, `COMPONENT`, or `EXTERNAL_SERVICE`. Each entry records ID, consumer, provider, necessity, availability, version constraint, fallback, and owner.

## Baseline dependencies

| ID | Consumer | Dependency | State |
|---|---|---|---|
| DEP-001 | All phases | Locked root blueprint and Phase 00 | AVAILABLE |
| DEP-002 | Phase 02 onward | Canonical capability labels | AVAILABLE |
| DEP-003 | Academic policy/calculation work | Applicable official CUI sources | REQUIRED / NOT YET VERIFIED |
| DEP-004 | Personal academic analytics | Imported, provenance-tagged personal record | OPTIONAL UNTIL IMPORT |
| DEP-005 | Knowledge integration | User-selected Obsidian vault and permission | CONFIGURATION REQUIRED |
| DEP-006 | AI features | Approved data-permission policy | REQUIRED BEFORE PROVIDER ACCESS |
| DEP-007 | Cloud/mobile | Stable CORE data and identity model | REQUIRED LATER |
| DEP-008 | Release | Selected and approved implementation stack | RESEARCH REQUIRED |

## Rules

An optional provider must have degraded behavior or a clear unavailable state. CORE cannot depend on cloud connectivity. Research candidates are not dependencies until selected. Versions are pinned only when implementation choices are approved. Cycles between authoritative documents must be removed by assigning one owner and one consumer.

## Review

Phase readiness checks must identify unavailable mandatory dependencies. A deferred dependency must not be smuggled into current acceptance criteria.
