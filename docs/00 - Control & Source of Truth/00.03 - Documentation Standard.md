# Documentation Standard

## Purpose

Define the minimum quality, structure, style, linking, and maintenance requirements for project documentation.
## Writing standard

Documents must be specific, testable, and understandable to the owner, future developers, and AI coding agents. Use calm plain language. Avoid filler, vague corporate language, false certainty, guilt-based phrasing, and duplicated boilerplate.

## Recommended structure

Use only headings relevant to the document: purpose, scope, ownership, capability level, concepts, rules, workflow, data, constraints, edge cases, failure handling, privacy, explainability, dependencies, examples, acceptance criteria, and open questions.

## Mandatory qualities

- State what the document owns and what it does not own.
- Separate current behavior from future capability.
- Label unresolved choices explicitly.
- Link to the authoritative owner rather than copying its definition.
- Use exact locked names and uppercase capability labels.
- Make deterministic rules precise enough to test.
- Identify privacy-sensitive data and permission boundaries.
- Include acceptance criteria for normative specifications.

## Markdown rules

Use one H1 matching the metadata title, ordered heading levels, fenced code blocks with language labels where useful, and readable tables. Links use repository-relative paths and must resolve once planned files exist. Do not use empty headings, placeholder-only sections, or `TBD` without an owner and resolution path.

## Review checklist

Check scope, authority, terminology, contradictions, capability drift, offline-first behavior, deterministic/AI boundaries, privacy, explainability, references, and acceptance criteria. A document is approved only after these checks and an explicit status change under `00.16`.
