# Cross-Document Conflict Resolution

## Purpose

Define a repeatable process for detecting, containing, resolving, and recording contradictions between project documents and sources.
## Conflict types

Conflicts may concern facts, terminology, ownership, requirements, capability timing, formulas, privacy, or paths. Difference is not automatically conflict: two documents may describe different scoped contexts.

## Resolution procedure

1. Quote the competing claims and identify exact paths/sections.
2. Determine each claim's owner, status, source class, scope, and applicable version/date.
3. Apply the authority order in `00.02` and provenance rules in `00.06`.
4. If one claim is clearly lower authority, correct it and audit dependents.
5. If authority is equal or scope is ambiguous, mark the issue `OPEN` and prevent consequential reliance.
6. Obtain the required official evidence or owner decision.
7. Update the authoritative owner, replace duplicates with references, log the change, and revalidate links.

## Special cases

Official policy applies only to its valid program/version/date. User-confirmed configuration cannot redefine external policy. Newer documents do not automatically outrank older frozen ones. Code does not overrule approved documentation merely because it is deployed; such mismatch is a defect or a formal change proposal.

## Safety behavior

Unresolved conflicts affecting grades, data loss, security, privacy, protected constraints, or meaningful automated changes block that behavior. Low-risk presentation conflicts may proceed with a visible provisional label.
