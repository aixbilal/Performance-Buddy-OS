# Database Migration During Updates

## Preflight

Inventory affected entities/projections, confirm current schema and migration ledger, verify keys/integrity/free space, stop competing writers, create and validate a recovery point, and prove the forward plus rollback-or-forward-recovery plan on representative copies.

## Execution

Acquire a migration lock; apply ordered, versioned, idempotent steps transactionally where possible; persist checkpoints outside ambiguous partial state; validate counts, hashes, references, revisions, source/provenance, and sampled domain semantics; rebuild disposable projections; then mark the schema ready.

Migrations never depend on AI or remote availability. Expand/migrate/contract supports compatibility when multiple app/protocol versions coexist. Destructive or irreversible transformations require explicit decision, export/backup, shadow-copy strategy, and user-impact disclosure.

Failure blocks unsafe writes, preserves original and recovery evidence, and enters a truthful repair/restore path. A new empty database is never substituted silently.

## Acceptance criteria

- Upgrade from every supported schema and interrupted-resume path passes.
- Before/after reconciliation proves no silent loss or semantic drift.
- Migration success is recorded only after full invariant validation.
