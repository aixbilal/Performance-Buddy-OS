# Release Strategy

## Lifecycle

A release progresses through scope freeze, dependency and version freeze, build, automated verification, security/privacy review, migration/restore rehearsal, accessibility and performance gates, signed artifact creation, staged distribution, monitoring, and closure.

Every candidate links source commit, dependency lock, build environment, application/schema/protocol versions, capability manifest, SBOM, test and evaluation snapshot, known issues, migration/rollback plan, checksums, signatures, and approvers. Rebuilding from the same declared inputs should produce identical or explainably equivalent artifacts.

## Deployment posture

Desktop is the initial primary release surface. Optional cloud services and AI providers have separate deployment/kill-switch state and cannot gate CORE startup. Rollout begins narrowly and expands only when error, migration, data-integrity, security, and performance signals remain within approved thresholds.

An emergency release may shorten cadence but not signing, migration safety, critical security, or data-integrity gates. Exceptions remain scoped, owned, expiring, and visible.

## Acceptance criteria

- Shipped artifacts are traceable to reviewed source and immutable evidence.
- A stopped rollout leaves existing installations usable and data intact.
- Post-release review records outcomes, incidents, and follow-up owners.
