# Versioning Strategy

## Version dimensions

Keep separate identifiers for application release, build, schema, record revision, domain definition/policy, calculation/rule, source, event, internal API/serialization, sync protocol, integration adapter, prompt/schema/tool, model/provider, capability label, and documentation baseline.

Application releases use an approved semantic scheme: major for intentionally breaking supported contracts, minor for backward-compatible capability, and patch for compatible fixes. Pre-release/build identifiers never alter compatibility meaning. Exact initial product version is a release decision, not inferred from documentation baseline `v1.0`.

## Rules

Published definitions and rules are immutable; supersession creates a new version. Historical results retain exact input/version manifests. New policies apply prospectively unless an explicit recalculation produces a new result. Capability labels such as `V1` are not software versions.

Compatibility is declared and tested rather than inferred from numeric ordering. Every artifact exposes machine-readable version and support information without including secrets.

## Acceptance criteria

- Historical calculations and AI runs resolve their exact dependencies or report a precise gap.
- No ambiguous generic `version` field crosses contracts.
- Release notes identify changed compatibility dimensions and user impact.
