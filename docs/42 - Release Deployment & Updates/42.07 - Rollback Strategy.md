# Rollback Strategy

## Principle

Rollback restores a known-good, compatible system state; it is not simply launching an older binary. Code, schema, data, protocols, providers, migrations, and sync state must be considered together.

## Options

Prefer rollout pause, feature/AI/provider kill switch, configuration rollback, or forward fix when data remains compatible. Binary rollback is allowed only if the older application explicitly supports the active schema and protocols. Otherwise restore the verified pre-update recovery point in isolation, reconcile impact, and obtain confirmation before activation.

Rollback planning records trigger thresholds, decision authority, artifact digests, compatible data range, backup ID, expected data-loss window, sync/device handling, verification, communication, and forward recovery. Post-update writes are never discarded without clear user impact and authorization.

Cloud/API rollback preserves compatibility windows and rejects unknown versions safely. Revoked or compromised artifacts remain blocked even if functionally older.

## Acceptance criteria

- Each release proves at least one safe recovery strategy before rollout.
- Tests cover post-migration writes, offline devices, sync, and interrupted rollback.
- Recovery validates signatures, schema, counts, hashes, and invariants before writes resume.
