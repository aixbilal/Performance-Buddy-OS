# Internal API Contracts

## Architecture

Internal APIs are application ports used by desktop, mobile, workers, integrations, and tests. They are not assumed to be network microservices. Interfaces expose use-case commands and queries rather than database tables.

## Contract envelope

Each request includes contract version, request/correlation ID, actor and device context, capability and permission context, expected entity revision where applicable, idempotency key for retryable commands, locale/timezone, and typed payload. Responses use typed success data or stable error/reason codes with safe details.

Commands validate and mutate through owning domains. Queries are side-effect free. Pagination, ordering, filtering, clocks, units, nullability, unknown states, and concurrency behavior are explicit. Sensitive fields require field-level authorization and are minimized.

## Compatibility

Additive changes remain backward compatible; breaking changes use a new version, migration window, consumer inventory, contract tests, and removal plan. No consumer infers behavior from undocumented fields.

## Acceptance criteria

- Contract tests cover UI, worker, mobile, and adapter consumers.
- Direct infrastructure access cannot bypass application APIs.
- Duplicate command delivery is safe where retry is supported.
