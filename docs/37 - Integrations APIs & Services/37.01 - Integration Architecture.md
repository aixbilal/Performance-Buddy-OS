# Integration Architecture

## Pattern

Each integration consists of an application-owned port, a provider-specific adapter, credential and permission boundary, normalized request/response schemas, provenance mapping, health and capability reporting, and contract tests. Domain services depend on ports, never vendor SDKs.

## Flow

Inbound data passes authentication where applicable, size/type limits, parsing, malware or content safety controls, schema validation, normalization, provenance creation, duplicate detection, and domain-command validation. Outbound work rechecks permission, consent, data zone, destination, cost/quota, and source revision immediately before sending.

## Failure isolation

Timeout, throttling, expired credentials, incompatible versions, malformed data, duplicate callbacks, partial results, and provider outages become normalized reason codes. Optional failures do not block unrelated CORE workflows. Retryable network operations use Phase 33 queues and stable idempotency keys.

## Versioning

Ports, payloads, adapters, mappings, and provider capabilities are versioned independently. Breaking contract changes require compatibility windows, migration, consumer tests, and rollback.

## Acceptance criteria

- Domain tests run against deterministic test adapters.
- Swapping providers does not change domain authority or stored meaning.
- Integration failure cannot corrupt canonical local data.
