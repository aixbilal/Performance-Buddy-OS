# Integration Permission Model

## Permission dimensions

Permissions are granted per integration, account or vault, domain/category, operation (`read`, `import`, `export`, `write`, `delete`, `subscribe`), purpose, resource scope, data zone, execution location, retention, and expiry. One permission never implies another.

## Lifecycle

Connection setup explains requested scopes, data categories, destination, purpose, provider processing, and degraded behavior. The application stores granted scopes and credential references—not plaintext secrets—and rechecks them before each consequential operation.

Users can inspect, pause, narrow, reauthorize, revoke, export, and delete integration state. Revocation stops new access, cancels eligible queued work, invalidates prohibited derivatives, and identifies remote data or tokens that require provider-side deletion.

## Rules

Use least privilege and incremental authorization. Background jobs, webhooks, imports, exports, AI, and UI actions use the same policy engine. Aggregates inherit the strictest contributing classification. Denial yields a narrower/manual path rather than fabricated data.

## Acceptance criteria

- Scope-escalation, expiry, revocation, account switch, and queued-work tests pass.
- Logs and errors never disclose credentials or prohibited content.
- Permission changes propagate to caches, derivatives, and subscriptions.
