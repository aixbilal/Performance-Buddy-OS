# Future Integration Registry

## Purpose

The registry records integration ideas without implying commitment, installation, endorsement, or access. Every entry begins as `FUTURE` until capability promotion and architecture approval are complete.

## Entry schema

Record registry ID, name, category, user problem, proposed direction (`inbound`, `outbound`, `bidirectional`), domains, data classes, required scopes, authority role, offline/degraded behavior, candidate providers/protocols, authentication, rate/cost assumptions, risks, dependencies, owner, status, evidence, decision link, and review date.

## Lifecycle

Statuses are proposed, researching, rejected, deferred, approved-for-prototype, and promoted. Promotion requires demonstrated user value, domain owner review, permission and threat model, data/provenance mapping, failure and recovery design, portability, accessibility where surfaced, provider exit plan, tests, and capability label assignment.

Registry entries cannot reserve domain authority, add hidden roadmap promises, or justify collecting credentials. Rejected and deferred entries retain reasons to prevent repeated ungrounded proposals.

## Acceptance criteria

- Every candidate has explicit scope, data exposure, owner, and decision status.
- UI and documentation cannot present unpromoted entries as available.
- Registry review detects stale assumptions and provider changes.
