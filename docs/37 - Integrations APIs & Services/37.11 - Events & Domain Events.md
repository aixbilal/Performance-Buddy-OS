# Events & Domain Events

## Distinction

A domain event records a completed domain fact after its transaction succeeds. An integration or analytics event communicates that fact to a consumer. Events are not commands and cannot instruct a domain to pretend an action occurred.

## Event contract

Events carry stable ID/type/version, owner entity and revision, occurred and recorded times, actor/device, domain, privacy class, minimum payload or owner references, idempotency key, correlation/causation IDs, provenance, and correction or supersession links.

## Delivery and consumption

Canonical data and an outbox/event record commit atomically where delivery is required. Consumers are idempotent, checkpointed, replayable, and tolerant of duplicate, late, reordered, corrected, and deleted facts. Disposable projections rebuild from compatible history.

Sensitive domains may suppress, redact, or aggregate events by permission. Event schemas evolve with old-event decoding and documented compatibility. Consumer failure never rolls back an already valid domain commit.

## Acceptance criteria

- Replay produces deterministic projections without duplicate effects.
- Corrections append or supersede rather than rewriting history silently.
- Event access cannot leak fields unavailable from the owning entity.
