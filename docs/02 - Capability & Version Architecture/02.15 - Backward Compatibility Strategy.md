# Backward Compatibility Strategy

## Purpose

Protect user data, workflows, integrations, and capability meaning as the product evolves through releases and intelligence levels.

## Compatibility dimensions

- **Data:** prior records remain readable and attributable.
- **Schema:** migrations are versioned, tested, reversible where feasible, and backed up.
- **Behavior:** deterministic results do not change silently; rule versions remain traceable.
- **Documents/contracts:** stable IDs and paths are preserved or formally migrated.
- **Integrations:** capability negotiation and clear unsupported states prevent corruption.
- **AI:** prompt/model changes preserve structured contracts or introduce a new version.

## Rules

New capabilities extend CORE contracts rather than embedding intelligence-only fields into mandatory workflows. Unknown fields are handled safely. Optional CLOUD/MOBILE metadata does not prevent local use. Removing a feature requires deprecation notice, export/migration path, and impact review.

Academic calculations retain the official rule/source version used at the time. Recalculation under a new policy is explicit, not silent history rewriting. Recommendation records retain model, context/provenance, validation, and approval outcome sufficient for audit.

## Breaking changes

A breaking change requires an approved decision, version increment, migration and rollback plan, backup, tests against representative old data, and user-facing explanation. The locked documentation tree itself follows Phase 00 revision policy.

## Acceptance criteria

Upgrades preserve confirmed local data; old records remain interpretable; disabling optional capability levels does not strand CORE data; and failures can be detected and recovered without pretending migration succeeded.
