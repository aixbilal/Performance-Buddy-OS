# Capability Registry

## Purpose

Provide the canonical index of capability labels, ownership, dependency rules, and readiness state.

## Registry

| Label | Primary owner phase | Kind | Depends on | Baseline state |
|---|---:|---|---|---|
| `CORE` | 23 and domain phases | Deterministic foundation | Local data and rules | COMMITTED |
| `LOCAL` | 25 | Intelligence level | Stable CORE contracts | PLANNED |
| `V1` | 26 | Intelligence level | CORE; optional LOCAL/CLOUD providers | PLANNED |
| `V2` | 27 | Intelligence level | Reliable evidence history and V1 contracts | PLANNED |
| `V3` | 28 | Intelligence level | Mature cross-domain data, rules, evaluation | FUTURE HORIZON |
| `CLOUD` | 34 plus provider phases | Deployment dimension | Explicit opt-in, sync/security contracts | OPTIONAL / DEFERRED |
| `MOBILE` | 36 | Surface dimension | Stable CORE data and sync/capture contracts | OPTIONAL / DEFERRED |
| `FUTURE` | Owning roadmap/domain | Commitment state | Approved promotion | NOT COMMITTED |

## Registration rules

Each feature record must include stable ID, name, domain owner, primary capability, optional dimensions, current status, dependencies, offline fallback, permissions, validation, approval behavior, acceptance tests, and promotion history.

Capabilities describe behavior, not marketing editions or software version numbers. A feature such as schedule creation may have a `CORE` editor, a `V1` natural-language proposal, and a `MOBILE` capture surface. These are separate contracts sharing domain entities.

## Status values

`PROPOSED`, `PLANNED`, `IN DEVELOPMENT`, `EVALUATING`, `AVAILABLE`, `DEGRADED`, `DEPRECATED`, and `RETIRED`. Status never overrides capability: a V3 idea marked AVAILABLE would still require V3 acceptance evidence and approval.

## Governance

Phase 02 owns classification; domain phases own meaning; roadmap phases own scheduling; release phases own shipped-version claims. Disputes follow Phase 00 conflict resolution.
