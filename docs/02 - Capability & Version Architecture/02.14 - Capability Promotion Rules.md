# Capability Promotion Rules

## Purpose

Define evidence and approval gates for moving a feature from future or lower maturity into a committed capability.

## Promotion principle

Promotion is an evidence-based scope decision, not a rename. A feature advances only when its current layer is useful, its dependencies are stable, and the next layer adds measurable value without weakening existing guarantees.

## Required proposal

Include capability ID, current/target labels, user problem, owner, dependencies, data/permission changes, offline behavior, deterministic boundary, human-approval behavior, risks, compatibility/migration, tests, evaluation thresholds, cost/latency, fallback, and rollback.

## Gates

1. **Scope:** aligns with Phase 01 and non-goals.
2. **Authority:** domain owner and source requirements are clear.
3. **Foundation:** required lower-level contracts are stable.
4. **Safety/privacy:** permissions, protected constraints, and threat implications pass review.
5. **Reliability:** deterministic and structured-output tests pass.
6. **Usefulness:** evaluation demonstrates benefit over simpler behavior.
7. **Compatibility:** existing data and workflows remain usable or have migration/rollback.
8. **Approval:** project owner records the decision and roadmap/release impact.

## Special rules

LOCAL/V1/V2/V3 promotion cannot transfer deterministic authority to AI. CLOUD promotion cannot make CORE remote-dependent. MOBILE promotion cannot silently displace desktop ownership. FUTURE items cannot skip directly to “available” based on a demo.

## Demotion

Unsafe, unreliable, costly, or unused capabilities may be disabled, deprecated, or returned to research while preserving data and documented compatibility.
