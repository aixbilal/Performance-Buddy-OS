# Version Ownership Matrix

## Purpose

Assign responsibility for defining, building, validating, approving, and communicating each capability level without confusing it with release versions.

## Ownership matrix

| Capability | Definition owner | Domain content owner | Validation owner | Promotion approval |
|---|---|---|---|---|
| `CORE` | Phase 02/23/33 | Relevant domain phase | Phase 40 + domain tests | Project owner |
| `LOCAL` | Phase 25 | Relevant domain + Phase 25 | Local benchmark/evaluation | Project owner |
| `V1` | Phase 26 | Relevant domain + Phase 26 | AI output, approval, safety tests | Project owner |
| `V2` | Phase 27 | Relevant domains + Phase 27 | Historical/predictive evaluation | Project owner |
| `V3` | Phase 28 | Cross-domain owners + Phase 28 | Safety, usefulness, longitudinal evaluation | Project owner |
| `CLOUD` | Phase 34/37/38 | Relevant service owner | Sync, security, recovery tests | Project owner |
| `MOBILE` | Phase 36 | Relevant domain + mobile owner | Mobile/offline/sync tests | Project owner |
| `FUTURE` | Phase 43/47 or named owner | Proposed domain | Research only until promoted | Project owner |

## Version distinctions

- Documentation baseline `v1.0` controls the documentation structure.
- Product release versions are defined in Phase 42.
- Capability labels identify behavior and maturity.
- Data/schema versions are owned by Phase 32.
- Prompt/model/evaluation versions are owned by their AI phases.

Changing one version does not silently change the others. A product release can contain CORE plus selected V1 features; “V1” must never be used as that release number.

## Conflict rule

The domain owner defines correctness, the capability owner defines delivery/authority boundaries, and validation owners define evidence. None may independently override Phase 00 governance or the locked product foundation.
