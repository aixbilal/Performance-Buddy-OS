# Surface Ownership Matrix

## Purpose

Separate desktop, mobile, background, local-AI, and cloud surfaces while preserving common domain ownership and local authority.

## Matrix

| Surface | Initial role | Allowed capability | Authority boundary |
|---|---|---|---|
| Desktop application | Primary command center | `CORE`, later `LOCAL/V1/V2/V3` | Local record is authoritative for CORE |
| Mobile companion | Fast capture, review, notifications | `MOBILE` plus exposed CORE contracts | Cannot silently replace desktop ownership |
| Local background work | Timers, schedules, indexing, local processing | `CORE/LOCAL` | Must be observable, recoverable, permission-scoped |
| Local AI runtime | Private classification/extraction/retrieval | `LOCAL` | Suggestions/outputs remain validated |
| Remote AI provider | Optional advanced assistance | `V1/V2/V3 + CLOUD` | Explicit data permission and failure fallback |
| Cloud sync service | Optional multi-device transport | `CLOUD` | No automatic claim over local truth |
| Obsidian vault | External knowledge store | Integration surface | Vault remains external and user-controlled |

## Ownership rules

Business meaning belongs to domain phases, not to a surface. A mobile marks-capture screen and desktop marks editor use the same academic provenance and validation contracts. Surfaces may optimize interaction but cannot redefine formulas, permissions, status semantics, or capability availability.

## Failure behavior

If an optional surface is unavailable, CORE continues locally. Queued or synchronized changes expose state and conflicts. Background and AI actions must not commit meaningful writes without the same rules applied to foreground actions.

## Future surfaces

New surfaces begin as `FUTURE` and require an owner, use case, permission model, offline/degraded behavior, compatibility impact, and promotion evidence.
