# Offline vs Cloud Capability Matrix

## Purpose

Make the offline-first promise testable by distinguishing mandatory local behavior from optional remote enhancement.

## Capability matrix

| Area | Offline CORE | Optional cloud behavior |
|---|---|---|
| Goals/plans/actions | Create, edit, schedule, reconcile | Sync across devices |
| Sessions/trackers | Run and record locally | Backup/sync after consent |
| Academic calculations | Full deterministic operation | No cloud authority required |
| Knowledge links/search | Local vault access/index where permitted | Optional remote enrichment |
| Analytics | Local deterministic summaries | Optional heavier analysis |
| AI | Product remains usable without it | Provider-assisted V1–V3 features |
| Backup/export | Local manual/automatic options | Optional encrypted remote backup |
| Identity | Local single-user profile | Optional device/account identity later |

## Classification rules

`CORE` cannot require network detection to succeed, remote authentication, remote feature flags, cloud-only secrets, or provider responses. Cloud-enhanced features declare latency, cost, data exposure, rate limits, unavailable state, and local fallback.

Synchronization is not backup; each has separate failure and recovery rules. Cloud copies do not automatically outrank local changes. Conflict policy belongs to Phase 34.

## Privacy and approval

Remote transfer is opt-in, minimized to the task, and visible. Permission for sync does not imply permission for AI processing. Provider access must be scoped by data category and revocable.

## Acceptance criteria

Airplane-mode tests cover all committed CORE workflows; cloud outages cannot corrupt local data; and UI/documentation never presents optional remote service as mandatory.
