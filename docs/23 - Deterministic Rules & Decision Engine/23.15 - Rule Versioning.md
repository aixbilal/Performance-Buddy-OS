# Rule Versioning

## Purpose

Preserve reproducibility as domain policies, formulas, thresholds, and validation behavior evolve.

## Version identity

Each rule has stable ID, semantic version, owner, status, effective scope/dates, source decision/policy, dependencies, implementation checksum where useful, migration behavior, fixtures, and supersession/deprecation links.

## Rules

Historical evaluations store the exact rule-set manifest and input snapshot hash. New versions apply prospectively unless an approved recalculation/migration is requested. Breaking semantic or output changes require explicit version increments and impact review. Academic policy versions remain distinct from engine software versions and capability labels.

## Deployment

Validate dependency closure and fixtures before activation; publish atomically; retain previous versions needed for history; support rollback without rewriting committed source data; and mark results stale when an unavailable version prevents reproduction.

## Acceptance criteria

Historical traces reproduce, parallel applicable policy versions can coexist, rollback is safe, migrations reconcile before/after outputs, and no rule changes silently in place.
