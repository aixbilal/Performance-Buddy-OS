# Validation Pipeline

## Purpose

Apply consistent gates to every consequential command before state changes occur.

## Pipeline

1. Authenticate local actor/context where applicable.
2. Authorize target, fields, and data categories.
3. Validate schema, type, units, and bounds.
4. Resolve identity, source, applicability, and versions.
5. Load an immutable fact/configuration snapshot.
6. Apply protected and hard constraints.
7. Apply domain invariants/calculations.
8. Evaluate conflicts, soft rules, and warnings.
9. Determine approval/confirmation requirements.
10. Return result and trace; commit separately and idempotently.

## Failure behavior

Failures are structured, localized, and non-mutating. Multiple actionable findings may be returned when safe. Storage failure after approval cannot be displayed as committed; retries use stable command IDs.

## Acceptance criteria

All interfaces share the pipeline, validation order is stable, unauthorized data is never loaded unnecessarily, and tests prove rejected commands produce no writes.
