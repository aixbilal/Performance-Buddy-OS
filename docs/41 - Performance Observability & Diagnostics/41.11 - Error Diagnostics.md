# Error Diagnostics

## Error contract

Errors use stable code/version, component, severity, retryability, user-safe message, technical reason code, correlation ID, operation state, affected scope, preserved/safe state, recovery actions, and cause chain of normalized codes.

## Behavior

Distinguish validation, authorization/consent, conflict, integrity, storage, migration, filesystem, network, provider, quota, cancellation, timeout, unsupported capability, and unexpected defects. The user sees what succeeded, what remains safe, and the next action; partial success is itemized.

Diagnostics never serialize arbitrary exception objects, SQL parameters, file contents, provider payloads, prompts, credentials, or private values. Expected operational failures are not reported as crashes. Unexpected failures preserve evidence without exposing content.

Recovery actions are idempotent and scoped: retry, cancel, rebuild disposable projection, reauthorize, export, restore, or seek support. No “repair” silently changes consequential records.

## Acceptance criteria

- Every major failure mode maps to a safe code and recovery path.
- Redaction failure blocks optional diagnostic export.
- Error reporting cannot claim success, freshness, or durability falsely.
