# 28.12 — Specialist Architecture

## Principle

Specialists are optional bounded analysis components, not personas with independent authority. Add them only when evaluation shows a simpler call or sequential workflow is insufficient.

## Specialist contract

Each specialist declares ID/version, purpose, owned question, allowed domain views, tools, output schema, evidence requirements, budgets, prohibited actions, and evaluation suite. It receives minimum permissioned context and returns findings/proposals—not writes.

Possible specialists may analyze academic allocation, development paths, recovery/load, scheduling feasibility, or evidence conflicts. Exact specialist set and orchestration are `RESEARCH REQUIRED` until benchmarked. Specialists do not communicate through uncontrolled free-form loops, delegate further, create memory, or expand permissions.

Outputs carry provenance, assumptions, confidence, conflicts, and expiration. Domain services and Phase 23 independently validate facts and proposed actions. Disagreement is preserved for manager synthesis rather than averaged into false consensus.

## Acceptance criteria

- Ablation tests demonstrate each specialist adds measurable value relative to complexity/cost.
- Permission isolation, tool bounds, loop limits, and failure containment pass.
- Removing a specialist leaves a defined simpler fallback and no orphaned authority.
