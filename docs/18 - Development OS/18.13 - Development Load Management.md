# Development Load Management

## Purpose

Keep technical learning and project work sustainable across normal weeks, examination periods, recovery needs, and changing academic risk.

## Inputs

Active modules/projects, deadlines, dependency readiness, recent evidence, cognitive load, session length, unresolved blockers, academic mode/risk, fixed commitments, sleep/recovery, and user priorities.

## Load states

`Progression`, `Normal`, `Maintenance`, `Reduced`, `Paused`, and `Recovery` are explicit planning states. Maintenance may use a small code-reading, retrieval, debugging, or implementation exercise without claiming full path progression.

## Rules

Limit simultaneous high-load paths. Prefer coherent blocks over excessive fragmentation. Avoid compensating for missed work by sacrificing sleep. During exams, preserve a minimum only when feasible; pausing is legitimate. On return, choose the smallest useful restart and review stale dependencies.

## AI boundary

`CORE` enforces constraints and configured limits. `V2` may propose load changes from evidence; the user confirms them.

## Acceptance criteria

Load fits real capacity, mode changes preserve history, maintenance remains honest, and accumulated backlog is reviewed rather than dumped into the next day.
