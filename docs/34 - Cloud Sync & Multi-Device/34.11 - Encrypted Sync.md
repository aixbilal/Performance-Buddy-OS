# Encrypted Sync

## Security requirements

Sync uses authenticated encryption in transit and encryption at rest. Keys, tokens, and recovery material are never stored in ordinary domain records or logs. Secret storage, access, rotation, expiration, revocation, backup, and recovery follow platform security controls and least privilege.

Payload classification determines whether data may leave the device. Local-only and never-cloud data are excluded before serialization. Metadata is minimized because identifiers, timing, and access patterns can also be sensitive.

## End-to-end encryption

End-to-end encryption may reduce provider visibility but affects server-side search, deduplication, recovery, conflict previews, key sharing, and multi-device enrollment. The product must disclose the chosen boundary accurately.

`RESEARCH REQUIRED`: select vetted cryptographic libraries, algorithms, key hierarchy, rotation and recovery design, and whether end-to-end encryption is feasible. No custom cryptography is permitted.

## Integrity and compromise

Clients verify authenticated payloads, revisions, and protocol context before applying changes. Suspected key compromise triggers revocation, rotation, session invalidation, containment, and an audit record.

## Acceptance criteria

- Plaintext secrets and prohibited data never appear in payloads or logs.
- Rotation and revocation are tested without losing valid records.
- Security claims match the implemented encryption boundary.
