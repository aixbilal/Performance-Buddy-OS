# Conflict Detection

## Conflict conditions

A conflict exists when an incoming change cannot be safely applied to the expected base state. Detection covers:

- concurrent revisions with no causal dominance;
- edit-versus-delete and restore-versus-delete races;
- incompatible schema or rule versions;
- uniqueness, ordering, or protected-constraint violations;
- divergent edits to the same non-mergeable field;
- stale devices attempting to recreate tombstoned records;
- corrupted payloads or missing dependency revisions.

## Detection method

Revision ancestry plus approved logical, vector, or equivalent causal metadata establishes whether one change follows another. Arrival time and device wall clocks are diagnostic evidence only.

Conflicts receive stable IDs and preserve entity identity, base revision, competing revisions, provenance, affected fields, reason codes, and safe previews. No branch is destroyed during detection.

## Automatic classification

Disjoint or mathematically commutative changes may be marked auto-mergeable only where a documented deterministic rule proves the result. Ambiguity becomes a surfaced conflict.

## Acceptance criteria

- Tests cover concurrent edit, edit/delete, stale resurrection, and schema mismatch.
- Both competing versions remain recoverable.
- Detection produces an explainable reason independent of provider timing.
