# Sync State Model

## States

Each synchronization unit exposes a durable state:

| State | Meaning |
|---|---|
| `LOCAL_ONLY` | Valid locally and not selected for cloud sync. |
| `QUEUED` | Eligible change awaits transmission. |
| `PUSHING` | Transmission is in progress; no success is assumed. |
| `PULLING` | Remote changes are being retrieved or verified. |
| `SYNCED` | Known eligible revisions are acknowledged at the recorded cursor. |
| `CONFLICT` | Concurrent or incompatible revisions require resolution. |
| `BLOCKED` | Consent, authentication, permission, schema, quota, or policy prevents progress. |
| `ERROR` | A retryable or terminal failure is recorded with reason. |
| `TOMBSTONED` | Deletion intent is retained for propagation and restoration policy. |

## State ownership

State is tracked per account, dataset, device, and operation as appropriate. A global “synced” badge must not hide partial failure. Checkpoints advance only after verified durable acknowledgement; retry attempts do not create a new domain effect.

## Transitions

Transitions carry reason codes, timestamps for observation, logical ordering, attempt counts, and audit references. Recovery from `BLOCKED`, `ERROR`, or `CONFLICT` is explicit and testable.

## Acceptance criteria

- UI status distinguishes local durability from remote synchronization.
- Partial success is visible at item level.
- Restarting the application preserves accurate state and cursors.
