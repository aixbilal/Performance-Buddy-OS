# Sync Failure Handling

## Failure classes

The system distinguishes network interruption, timeout, authentication expiry, revoked device, permission or consent denial, quota or rate limit, provider outage, incompatible protocol or schema, integrity failure, partial acknowledgement, cursor invalidation, storage exhaustion, and domain conflict.

## Response policy

- Retry transient failures with bounded exponential backoff and jitter.
- Stop and request action for revoked credentials, denied consent, or incompatible versions.
- Honor provider retry guidance without unbounded battery, bandwidth, or cost use.
- Preserve durable queue items and last verified cursors across restarts.
- Quarantine corrupt or unverifiable content; never partially apply it.
- Display item-level reason codes, last attempt, and next safe action.
- Keep local workflows available unless local integrity is itself at risk.

No failure path may claim `SYNCED` without verified durable acknowledgement. A kill switch can disable remote exchange while retaining local data and diagnostic evidence.

## Recovery testing

Tests inject disconnection, duplicate delivery, reordered operations, partial batches, expired credentials, quota exhaustion, corrupted payloads, provider downtime, and client crashes.

## Acceptance criteria

- Retrying is idempotent and bounded.
- Terminal failures require explicit resolution rather than endless retry.
- Recovery never silently overwrites or loses a valid revision.
