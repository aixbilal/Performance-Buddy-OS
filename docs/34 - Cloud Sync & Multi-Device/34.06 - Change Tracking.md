# Change Tracking

## Change envelope

Every eligible change has a stable operation ID, entity type and ID, base and resulting revision, origin installation and device IDs, logical or causal ordering data, schema and protocol versions, operation kind, payload hash, creation time, consent and permission context, and processing state.

Payloads contain the minimum data needed to reproduce the authorized change. Secrets, unrestricted diagnostics, and local-only fields are excluded. Sensitive values are encrypted according to their classification.

## Recording rules

- Record the change atomically with the local domain commit.
- Treat operation IDs as idempotency keys across retries and devices.
- Retain tombstones long enough to prevent stale-device resurrection.
- Preserve provenance through import, merge, restore, and resolution.
- Compact logs only after every required checkpoint and retention rule permits it.
- Never infer causality from wall-clock order alone.

## Integrity

Hashes detect accidental corruption but do not replace authenticated transport or signatures where required. A mismatched envelope is quarantined and audited rather than partially applied.

## Acceptance criteria

- A crash cannot leave a committed eligible mutation untracked.
- Replaying an operation produces no duplicate domain effect.
- Change records support conflict explanation without leaking excluded data.
