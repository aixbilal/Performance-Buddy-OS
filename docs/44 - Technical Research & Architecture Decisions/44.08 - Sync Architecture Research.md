# Sync Architecture Research

## Decision

Select operation/change protocol, causal ordering, conflict/merge strategy, cursor/checkpoint model, tombstone retention, resnapshot, transport, and hosted components for optional sync.

## Options and criteria

Compare custom operation log, change-data APIs, replicated database approaches, CRDTs where semantics justify them, and managed sync systems. Evaluate local authority, idempotency, causal correctness, deterministic merge boundaries, schema evolution, delete/restore, device revocation, encryption/E2EE, offline duration, attachments, observability, provider portability, performance, cost, and debuggability.

## Prototype

Use randomized multi-device state-machine tests for replay, reorder, partial acknowledgement, clock skew, long offline, same/disjoint edits, edit/delete, stale resurrection, schema mismatch, key rotation, provider outage, and resnapshot. Verify convergence and preserved branches.

Wall-clock last-write-wins is not acceptable for meaningful data. Complexity requires demonstrated product need.

## Research status

`RESEARCH REQUIRED`: no protocol, merge algorithm, transport, or server architecture is approved.

## Acceptance criteria

- Candidate behavior is modeled against Phase 34 contracts.
- Conflict explanations do not depend on arrival time.
- The ADR includes migration and provider-exit tests.
