# 25.13 — Local AI Fallbacks

## Principle

Fallback is designed per application before release. Failure must reduce convenience, not correctness, user control, or access to trusted CORE records.

## Fallback order

1. Retry once only when the failure is transient and the operation is idempotent.
2. Use a smaller or alternate local configuration only if it independently passed the same task gates.
3. Offer the deterministic form, search, calculation, or manual workflow.
4. Offer optional `CLOUD` execution only with explicit task- and data-scoped consent and full disclosure.
5. Save the user’s draft and clearly mark the feature unavailable.

Fallback triggers include unsupported hardware, memory or thermal pressure, missing/corrupt model, runtime failure, timeout, low confidence, invalid structure, insufficient evidence, permission denial, and cancellation. A cloud path is never automatic merely because local inference failed.

## Recovery

Failures produce no trusted mutation. The system releases resources, invalidates uncertain partial output, preserves safe input, records a redacted reason, and offers repair/reinstall controls when applicable. Circuit breakers prevent repeated startup or download loops.

## Acceptance criteria

- Every local application documents triggers, user message, retained state, and next action.
- Fallback tests prove no duplicate writes, privacy downgrade, or CORE startup dependency.
- Disabling and uninstalling local AI leave user data and deterministic workflows intact.
