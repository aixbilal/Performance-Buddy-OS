# 25.07 — Command Parsing

## Purpose

Convert natural-language input into a proposed command envelope for a registered application command. Parsing improves speed; it never executes the command.

## Output contract

The envelope contains command ID, schema version, extracted slots, normalized values, unresolved references, assumptions, confidence per material slot, source spans, and clarification need. Only allowlisted commands and fields may appear.

## Flow

1. Apply user/session permissions and identify eligible command families.
2. Parse locally within a bounded input length.
3. Strictly validate schema and resolve entity identifiers through domain services.
4. Reject unsupported commands, invented entities, invalid units, and ambiguous dates.
5. Show a human-readable preview or ask a focused clarification.
6. Apply Phase 23 validation and the command’s confirmation policy.
7. Execute separately with idempotency and audit.

High-consequence commands, bulk edits, destructive changes, and external actions always require explicit confirmation. Confidence never replaces confirmation or deterministic validation.

## Acceptance criteria

- Tests cover paraphrases, typos, negation, ambiguity, dates, units, multiple intents, and injection attempts.
- False execution is impossible because parsing has no write authority.
- Unsupported or low-confidence input falls back to forms/search without losing the original text.
