# 25.12 — Local Model Benchmark Plan

## Objective

Produce reproducible evidence for selecting a model/runtime/quantization per task and hardware tier. The benchmark does not crown one universal model.

## Benchmark matrix

Test command parsing, classification, extraction, structured output, embeddings/retrieval, and bounded grounded synthesis where proposed. Cross these with representative hardware tiers, context lengths, data sensitivity classes, language needs, cold/warm start, battery/AC state, and supported acceleration backends.

## Recorded measures

Record task quality and safety metrics from 25.04, time to first result, total latency, throughput, peak resident and device memory, model/package size, load time, energy proxy, sustained thermal behavior, crashes, cancellation time, and schema/permission failures. Store OS, drivers, runtime, model hash/version, quantization, prompt/schema, settings, dataset revision, and benchmark harness revision.

## Method

Freeze datasets and thresholds before final comparison; use repeated runs and report variation, not only averages. Separate development and holdout cases. Include failure, ambiguity, injection, inaccessible-source, and low-resource tests. Publish limitations and rejected configurations.

## Acceptance criteria

- Results are reproducible from a versioned manifest without exposing private datasets.
- Promotion evidence maps to Phase 24.17 and a declared hardware support tier.
- Regression benchmarks run before model, runtime, prompt, schema, or quantization updates.
