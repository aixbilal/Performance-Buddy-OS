# 33.11 — Recovery After Connectivity

## Recovery sequence

Detect stable relevant connectivity; authenticate destination; refresh permissions/consent/configuration; inspect queue; discard/cancel expired or revoked work; validate payload/source revisions; order dependencies; send with idempotency; record acknowledgements; pull remote sync changes through Phase 34; surface conflicts; rebuild affected projections; and report results.

## Rules

Recovery is incremental, bounded, pausable, and yields to interactive local work. Remote state never overwrites divergent local revisions silently. Partial success is represented per item. Ambiguous remote mutation outcome stops retries until reconciled. Provider/cloud failures do not roll back already committed local domain changes.

Notifications consolidate and avoid “back online” noise when nothing requires attention.

## Acceptance criteria

- Long-offline, large queue, partial acknowledgement, revoked device, stale token, conflict, and interruption tests pass.
- Repeated reconnect produces the same final acknowledged state without duplicates.
- Users can continue local work during recovery.
