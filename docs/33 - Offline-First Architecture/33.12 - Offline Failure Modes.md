# 33.12 — Offline Failure Modes

## Failure catalog

Database unavailable/locked/corrupt; migration failure; disk full/read-only; permission loss; missing/moved file; corrupt index/cache; clock/timezone error; duplicate scheduler run; local model failure/resource pressure; queue corruption/growth; network flapping; stale credentials; partial remote acknowledgement; sync conflict; backup misconception; and UI falsely claiming completion/freshness.

## Containment

Fail closed for unsafe writes, permissions, integrity, migrations, and ambiguous remote effects. Preserve originals and drafts; use transactions, checksums, leases, idempotency, bounded retries, quarantine, verified backups, repair tools, and read-only mode where safe. Never create a blank database, discard a queue, or “repair” consequential values silently.

## User recovery

State what remains safe, what failed, last verified backup/sync, and available retry, export, restore, rebuild, cancel, or support path. Distinguish local data from unsynced remote enhancements.

## Acceptance criteria

- Fault injection covers every catalog class at each critical transition.
- Recovery proves no silent loss, duplicate writes, privacy downgrade, or false success.
- Kill switches isolate optional sync/AI/search components while CORE data remains accessible where integrity permits.
