# Sensitive Data Redaction

## Scope

Redaction applies before data enters logs, telemetry, crash reports, support bundles, notifications, UI previews, screenshots generated by the product, exports, AI context, or third-party errors. It is a boundary control, not a substitute for avoiding collection.

## Method

Use schema-aware allowlisting first: emit only approved fields. Apply typed redactors for credentials, identifiers, paths, URLs/query strings, headers, free text, academic/financial/routine values, and media metadata. Replace values with stable non-reversible tokens only when correlation is necessary.

Redaction occurs at the earliest boundary and again before egress. Error objects and nested provider responses are normalized rather than serialized wholesale. Derived summaries that reveal protected values inherit the source restriction.

Pattern matching can miss novel secrets and can over-redact; it supplements, not replaces, typed contracts and tests. Redaction keys and dictionaries are protected and versioned.

## Acceptance criteria

- Seeded and property-based tests cover nested, encoded, multiline, URL, header, filename, and model-output leaks.
- Failure in redaction blocks optional egress rather than sending raw data.
- Redacted diagnostics remain useful through safe IDs and reason codes.
