# Database Encryption

## Requirement

The local database must support an approved encryption-at-rest design integrated with Phase 33 durability, migration, backup, and recovery requirements. Encryption protects lost media and offline copying; it does not replace access control, process isolation, or device security.

## Key boundary

Database keys are generated with a cryptographically secure mechanism and stored or wrapped using approved OS secret storage or an equivalent protected boundary. Keys never appear in source code, ordinary configuration, domain tables, logs, analytics, crash reports, or AI context.

Rotation, backup, recovery, device migration, user sign-out, lost-key behavior, and secure deletion limitations are defined before release. Backups and exports require their own encryption and key lifecycle. A failed decrypt must not trigger blank database creation.

## Research gate

`RESEARCH REQUIRED`: select database engine/extension, vetted library, cipher parameters, key derivation and wrapping, unlock UX, rotation, recovery, performance limits, and platform support after threat modeling and benchmarks.

No custom encryption format or algorithm is permitted.

## Acceptance criteria

- Wrong/missing key, interrupted rotation, restore, migration, and tamper tests fail safely.
- Plaintext database content is absent from logs and temporary copies.
- Recovery exercises prove authorized users can restore without weakening key controls.
