# Security Incident Recovery

## Lifecycle

Security incident handling follows preparation, detection, triage, containment, evidence preservation, eradication, recovery, communication, and post-incident improvement. Safety and data integrity take priority over maintaining optional service availability.

## Incident record

Record incident ID, discovery and occurrence windows, reporter, affected versions/devices/accounts/data zones, indicators, severity and confidence, containment actions, evidence custody, notifications, recovery verification, root cause, corrective actions, owners, deadlines, and closure approval. Do not copy exposed secrets into the record.

## Response actions

Available controls include cloud/integration kill switches, queue pause, device/session revocation, secret/key rotation, provider isolation, signed fixed release, backup preservation, clean restore, derivative purge, user guidance, and increased monitoring. Evidence is read-only and privacy-scoped.

Recovery verifies package signatures, database integrity, authorization, keys, migrations, sync state, and restored counts/hashes before normal writes resume. Compromised credentials are rotated even if leaked copies appear deleted.

`RESEARCH REQUIRED`: severity matrix, contacts, notification/legal duties, evidence tooling, and exercise cadence.

## Acceptance criteria

- Exercises cover leaked token, lost device, malicious update, cloud breach, and local corruption.
- Recovery time/data-loss outcomes are measured against approved objectives.
- Post-incident actions update threats, tests, controls, and documentation.
