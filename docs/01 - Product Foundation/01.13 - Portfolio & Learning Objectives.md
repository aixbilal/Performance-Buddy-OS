# Portfolio & Learning Objectives

## Purpose

Define how building Performance Buddy OS should demonstrate engineering capability and strengthen independent technical judgment for the project owner.

## Portfolio objective

The project should demonstrate disciplined product and software engineering: requirements, domain separation, deterministic rules, local data, privacy, adaptive planning, explainable AI, testing, recovery, and deliberate evolution from a personal tool toward optional future capabilities.

The portfolio story is not “AI generated a large application.” It is that the owner identified a real problem, designed a governed architecture, made explicit trade-offs, implemented reliable slices, evaluated results, and can explain the system.

## Learning objectives

- Understand frontend, desktop, data, and integration architecture rather than copying generated code.
- Implement and test deterministic calculations and rule systems.
- Learn schema design, migrations, backup, recovery, and offline behavior.
- Practice debugging, profiling, accessibility, security, and code review.
- Build AI features with structured outputs, retrieval, tool boundaries, evaluation, and approval workflows.
- Compare technologies through evidence and ADRs before selection.
- Maintain documentation and implementation consistency.

## AI-assisted engineering boundary

AI may accelerate research, drafting, implementation, testing, and review. The owner must be able to trace important logic, run tests, explain key design choices, and modify the code without blindly depending on generated output. Dedicated AI-off practice and human learning checkpoints remain part of the project.

## Evidence

Useful portfolio evidence includes approved ADRs, architecture diagrams, reproducible tests, migration/recovery demonstrations, performance measurements, AI evaluation results, accessibility checks, and concise explanations of trade-offs. Feature count and code volume are weak evidence by themselves.

## Scope discipline

Learning value does not justify unnecessary complexity. Choose the simplest architecture that teaches and satisfies the real requirement; introduce advanced patterns only when their need can be demonstrated.
