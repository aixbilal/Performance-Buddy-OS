# Portability Requirements

## Principle

The user can leave a framework, device, or optional provider without losing access to understandable personal data. Portability includes meaning, relationships, provenance, and documented limitations—not merely raw table dumps.

## Requirements

Exports use documented, versioned, non-proprietary formats where practical and include schema manifests, IDs, revisions, timestamps/timezones, units/currencies, enums and unknown states, relationships, deletion markers where authorized, checksums, and provenance. Attachments retain safe names, hashes, MIME/type, and references.

Provider-specific fields are normalized or explicitly placed in namespaced extensions. Secrets and credentials are excluded. The format supports streaming for large data, deterministic validation, partial-scope export, and forward-compatible unknown fields.

Importers publish supported versions, mapping rules, losses, defaults, and migration paths. A user can verify an export without the original provider. Obsidian and other external sources remain separately owned and are referenced unless selected for export.

## Acceptance criteria

- A clean installation can import a supported full export and reconcile declared invariants.
- Provider exit rehearsal demonstrates usable data without proprietary APIs.
- Unsupported or lossy fields are disclosed before export/import confirmation.
