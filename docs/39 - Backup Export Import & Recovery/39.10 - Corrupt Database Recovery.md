# Corrupt Database Recovery

## Detection

Signals include database integrity-check failure, invalid pages/checksums, impossible constraints, migration-ledger mismatch, unreadable encryption state, repeated I/O failure, or reconciled invariant mismatch. Suspected corruption blocks unsafe writes and never triggers blank-store creation.

## Recovery order

1. Stop writers and optional sync/jobs.
2. Preserve the original database, journals, logs, version metadata, and relevant environment evidence read-only.
3. Diagnose storage, key, engine, and schema causes without modifying evidence.
4. Prefer restoration from the newest verified clean backup.
5. If necessary, use approved engine recovery into a separate candidate database.
6. Validate counts, hashes, references, revisions, audit continuity, attachments, and domain invariants.
7. Report salvaged, lost, quarantined, and uncertain records.
8. Obtain confirmation and atomically activate only a verified result.

Never run unreviewed repair commands on the only copy. Recovered uncertain values retain provenance and do not become authoritative automatically.

## Acceptance criteria

- Injected corruption tests exercise detection, containment, restore, and salvage.
- Recovery evidence is privacy-safe and preserves root-cause investigation.
- The user sees measured loss/uncertainty before activation.
