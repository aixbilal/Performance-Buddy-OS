# Backup Strategy

## Objective

Backups preserve recoverable historical state against deletion, corruption, ransomware, software defects, failed migration, device loss, and operator error. They are independent from active synchronization, which can propagate damage.

## Strategy

Use multiple recovery points, protected retention, encryption, integrity manifests, and more than one failure boundary where practical. Define recovery point objective, recovery time objective, scope, frequency, retention, ownership, storage location, key recovery, deletion behavior, and restore verification for each backup class.

Back up canonical database state, required attachments/configuration, schema and application versions, migration ledger, and a manifest of included and excluded assets. Disposable caches and regenerable indexes are normally excluded. External sources such as an Obsidian vault are referenced, not silently copied, unless separately selected.

## Proof

A created archive is only a candidate backup. Verification checks completeness, authentication/integrity, decryptability, compatibility, and restoration into an isolated location. Scheduled drills measure actual recovery.

`RESEARCH REQUIRED`: approve RPO/RTO, media/location strategy, rotation, retention, and supported versions.

## Acceptance criteria

- Sync and provider replication are never presented as backup.
- Loss of one device or location does not invalidate the entire approved strategy.
- Restore drills recover a known snapshot with reconciled invariants.
