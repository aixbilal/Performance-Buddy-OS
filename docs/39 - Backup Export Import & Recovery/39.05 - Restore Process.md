# Restore Process

## Preflight

Restore operates into an isolated staging location. It verifies artifact authentication and checksums, encryption/key access, manifest completeness, application/schema compatibility, available storage, source identity, attachments, and migration path before touching the active store.

## Workflow

1. Select and inspect a recovery point.
2. Preserve the current store with a verified safety snapshot where possible.
3. Decrypt and extract into isolated storage.
4. Open read-only and run integrity, counts, hashes, references, revisions, and domain-invariant checks.
5. Apply tested migrations if required and revalidate.
6. Preview recovery time, excluded/newer data, and sync consequences.
7. Obtain explicit confirmation.
8. Atomically switch to the verified restored store.
9. Rebuild disposable projections and reconcile devices/sync without stale resurrection.

Restore never merges implicitly. Merge/import of selected records uses Phase 39.07 instead. Failure leaves the active store intact and produces privacy-safe diagnostics.

## Acceptance criteria

- Interrupted restore cannot leave an ambiguous active store.
- Tests cover old versions, missing attachments, wrong keys, and active sync.
- Post-restore validation proves the selected recovery point is active.
