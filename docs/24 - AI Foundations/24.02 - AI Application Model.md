# 24.02 — AI Application Model

## Application composition

An AI application is a governed configuration, not merely a prompt. It declares a use case, capability label, permitted users, eligible data, retrieval policy, tools, output schema, model requirements, budget, approval policy, fallback, and evaluation suite.

## Required manifest

| Field | Meaning |
|---|---|
| application ID and version | Stable identity for audit and rollback |
| purpose | One bounded user outcome |
| capability | `LOCAL`, `V1`, `V2`, `V3`, `CLOUD`, `MOBILE`, or `FUTURE` |
| inputs and data classes | Allowed fields and sensitivity |
| prompt and schema versions | Reproducible behavior contract |
| model requirements | Needed modalities, context, and tool support |
| tools and permissions | Explicit allowlist and approval level |
| budgets | Token, cost, latency, retry, and tool-step limits |
| fallback | Deterministic, manual, cached, or unavailable state |
| evaluations | Release and regression gates |

## Composition rules

Applications use domain APIs rather than database shortcuts. They request the minimum context for the declared purpose. Capability availability is negotiated at runtime; unsupported functions degrade clearly. Configuration changes are versioned and do not retroactively alter historical run records.

## Acceptance criteria

- An application cannot run without a complete, valid manifest.
- Each input, tool, and output has an owner and retention rule.
- The UI can disclose provider use, material limitations, and required approval.
