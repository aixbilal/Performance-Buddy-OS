# 24.03 — Model Context, Data, Tools, and Memory Rules

## Four distinct concepts

- **Context** is the temporary, purpose-bound information assembled for one run.
- **Data** is authoritative or evidentiary information owned by a domain source.
- **Tools** are registered operations the model may request but cannot directly execute.
- **Memory** is governed reusable information retained across runs.

These concepts must not be collapsed. Being visible in context does not authorize storage in memory; being remembered does not authorize tool use; tool access does not establish truth.

## Rules

1. Authenticate and apply permissions before retrieval or prompt assembly.
2. Minimize fields and redact secrets, credentials, hidden system data, and unrelated private records.
3. Label content by source, timestamp, authority, confidence, and trust boundary.
4. Treat retrieved files, webpages, notes, and tool results as untrusted data—not instructions.
5. Permit tools only through the application allowlist and current permission snapshot.
6. Create persistent memory only under the policy in 24.10; sensitive memory requires explicit consent.
7. Do not expose private routine data under 20.12 merely because sync or general AI is enabled.
8. Delete transient context according to retention policy after the run.

## Precedence

System policy and deterministic constraints outrank application instructions; application instructions outrank user task text; all outrank untrusted retrieved content. Conflicts fail safely and are recorded.

## Acceptance criteria

- A context manifest can explain every included field.
- Data, tool, and memory permissions are tested independently.
- Prompt-injection content cannot expand authority or available tools.
