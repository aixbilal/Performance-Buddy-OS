# 24.05 — Structured Outputs

## Purpose

Structured outputs make model proposals machine-checkable. They do not make them correct or authoritative.

## Contract

Every machine-consumed response uses a versioned schema with stable identifiers, required fields, enumerations, length and numeric bounds, null behavior, and forward-compatibility rules. Material recommendations include evidence references, assumptions, confidence, uncertainty, reason codes, and proposed—not committed—actions.

## Validation pipeline

1. Parse strictly; reject trailing or ambiguous content.
2. Validate schema, types, ranges, identifiers, and schema version.
3. Resolve referenced entities through owned domain services.
4. Check provenance, permissions, and evidence availability.
5. Recompute deterministic values in CORE.
6. Apply Phase 23 constraints and recommendation validation.
7. Request approval where policy requires it.
8. Commit through a separate transactional command.

Unknown fields are ignored only when the schema explicitly permits them. Invalid outputs may receive one bounded repair attempt when no tool or write has occurred; otherwise they fail safely. Raw model text is never coerced into trusted records.

## Acceptance criteria

- Schemas are versioned, testable, and backward-compatible by declared policy.
- Validation errors are user-safe and diagnostically useful.
- No structured result can directly write a source-of-truth record.
