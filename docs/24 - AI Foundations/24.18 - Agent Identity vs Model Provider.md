# 24.18 - Agent Identity vs Model Provider
## Canonical distinction

An **AGENT** is an application-owned role with persona, scoped memory, tools, objectives, permissions, policies, and identity version. A **MODEL PROVIDER** supplies inference through a replaceable adapter: local runtime, Gemini, Groq, or a future provider. An **API KEY** is a secret credential authorizing a provider account/project or endpoint.

These are separate entities and mappings. Three keys do not imply three agents; one agent may use several eligible providers over time, and several agents may share a provider subject to budgets and permissions. A visible companion is never permanently coupled to a key, endpoint, vendor, or model.

## Authority and lifecycle

Agent identity and memory continuity are application data. Providers return proposals and structured results; they do not own persona state or deterministic facts. Credentials remain in the secret store, referenced only by opaque IDs, and never enter prompts, logs, exports, or agent memory.

Routing changes may affect capability, latency, privacy disclosure, and confidence, but not the agent's permissions or identity. Provider replacement requires compatibility evaluation and audit records. Models do not retrain themselves from conversations; application memory improves future context through explicit capture, retrieval, summarization, and permission-controlled updates.

## Acceptance criteria

- Schemas represent agents, providers/models, and credentials separately.
- Removing a key cannot delete or reset an agent.
- Switching providers preserves persona and memory while disclosing material capability changes.
- No provider response can alter its agent profile or permission scope without approved application logic.
