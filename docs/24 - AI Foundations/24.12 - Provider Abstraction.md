# 24.12 — Provider Abstraction

## Purpose

Provider abstraction keeps domain logic and product behavior independent of a specific model vendor. A provider adapter translates the common application contract into provider requests and normalizes responses, usage, errors, tool calls, and safety signals.

## Capability negotiation

Adapters declare supported modalities, context limits, structured-output guarantees, tool calling, streaming, locality, data-processing region, retention controls, pricing metadata, and rate-limit semantics. Selection uses the application’s minimum requirements plus user privacy and cost settings. Unsupported capability fails clearly or uses an approved fallback; it is never silently emulated with weaker guarantees.

## Reproducibility

Run records store provider, model identifier, model revision when exposed, adapter version, parameters, region, and feature flags. Secrets remain in a credential boundary and never enter prompts, logs, or client-visible configuration.

Provider-specific fields terminate at the adapter. Domain services receive normalized evidence and proposals only.

## Acceptance criteria

- Contract tests run against each adapter and a deterministic test double.
- Switching providers does not change domain authority or approval rules.
- Provider selection and remote data exposure are disclosed when relevant.
