# 24.13 — Provider Failure Handling

## Failure classes

Failures include unavailable service, timeout, malformed output, content refusal, unsupported capability, authentication error, context overflow, rate limit, safety block, partial stream, and uncertain tool status. They are normalized without hiding provider detail needed for operations.

## Response policy

- Fail closed for permissions, validation, credentials, and uncertain writes.
- Retry only transient, idempotent operations with bounded exponential backoff and jitter.
- Never retry a meaningful mutation without an idempotency key and known prior outcome.
- Reduce context or select an approved provider only when privacy, capability, and user settings still hold.
- Preserve the user’s draft and show a clear retry, manual, or deterministic path.
- Keep CORE workflows available; do not corrupt source data or claim completion.

Partial streaming content is presentation-only until the final structured result validates. Circuit breakers prevent repeated failing calls. Recovery records the original and fallback attempts under one correlation chain.

## Acceptance criteria

- Each failure class has retryability, fallback, disclosure, and telemetry rules.
- Chaos tests confirm no mutation on ambiguous provider outcomes.
- Recovery cannot silently downgrade privacy or capability guarantees.
