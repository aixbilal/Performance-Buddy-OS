# 24.06 — Tool Calling

## Model

A model may propose a tool call; the application executes it only after independent authorization and validation. Tools are registered server-side with stable names, typed arguments, bounded outputs, ownership, sensitivity, side-effect class, timeout, idempotency behavior, and approval policy.

## Classes

- **Read:** retrieves permitted information without mutation.
- **Compute:** performs deterministic calculation without mutation.
- **Draft:** creates an uncommitted candidate.
- **Write:** changes trusted state and normally requires preview and approval.
- **External action:** affects another system or person and requires explicit confirmation.

## Execution rules

Use least privilege and an application-specific allowlist. Recheck authorization at execution time. Validate entity IDs and ranges; do not accept paths, queries, or commands outside the declared contract. Bound tool steps, output size, runtime, and recursion. Use idempotency keys for retryable mutations. Return structured success, refusal, partial, or failure results without leaking secrets.

Tool output is untrusted context. The model cannot treat an instruction embedded in a note or external result as authority. Parallel calls are allowed only when independent and side-effect free.

## Acceptance criteria

- Every call records run ID, tool version, redacted arguments, authorization decision, outcome, and latency.
- Writes have preview, applicable approval, conflict detection, and recovery behavior.
- Tests prevent unauthorized tools, argument injection, duplicate writes, and infinite loops.
