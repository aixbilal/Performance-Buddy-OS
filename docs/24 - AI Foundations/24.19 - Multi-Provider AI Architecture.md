# 24.19 - Multi-Provider AI Architecture
## Purpose and topology

Define a provider-neutral inference pool supporting a local model, configured Gemini endpoints/projects, Groq, and future replaceable providers. Domain services call typed AI capabilities through the existing provider abstraction, never vendor SDKs directly.

Adapters declare modality, context window, structured output, tool calling, locality, retention, region, latency, availability, and cost/rate metadata. Routing filters first by permission and required capability, then uses user policy, offline state, task class, health, budget, and quality evidence. Local-first is mandatory for local-only data and preferred for offline continuity.

## Boundaries

Provider pools improve resilience and fit; they are not quota-circumvention systems. Routing must not rotate keys to evade provider limits, terms, safety controls, or account restrictions. Multiple keys/projects are explicit credential configurations with legitimate ownership and auditable selection.

Normalized results include provider/model/version provenance, confidence signals, validation status, and errors. Deterministic facts remain authoritative. Every consequential proposal proceeds to rules validation and human review.

## Acceptance criteria

- A provider can be added or removed without rewriting agent or domain logic.
- Offline use has a declared local/deterministic fallback.
- Remote exposure is permission-checked and disclosed before transmission when required.
- Health/rate-limit handling uses bounded backoff and approved failover, never evasion.
