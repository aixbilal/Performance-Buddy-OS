# 24.17 — AI Feature Evaluation Gates

## Gate principle

An AI feature is not promoted because a demonstration looks useful. It advances only when a versioned evaluation suite shows that it meets capability-specific quality, safety, privacy, reliability, latency, and cost thresholds.

## Required evaluation groups

- schema adherence and deterministic recomputation;
- grounding, citation correctness, abstention, and conflict handling;
- tool selection, argument validity, idempotency, and approval enforcement;
- permission isolation, sensitive-data leakage, retention, and deletion;
- prompt-injection and malicious tool-output resistance;
- hallucination, misleading certainty, boundary refusal, and explanation quality;
- provider failure, cancellation, retry, rate-limit, and offline fallback;
- latency, token use, cost, accessibility, and user control;
- domain-specific scenarios and regression against prior approved versions.

## Promotion process

Define datasets and thresholds before testing. Separate development, evaluation, and production evidence. Record model, prompt, schema, tools, policies, provider adapter, dataset revision, and results. Human review covers high-impact cases. Failed required gates block promotion; waivers require an owner, rationale, scope, expiry, and compensating control.

Capability promotion follows 02.14. Production monitoring can trigger disablement or rollback, but monitoring data does not replace pre-release evaluation.

## Acceptance criteria

- Every released AI application has an evaluation report and regression suite.
- Required gates cannot be bypassed by changing provider or prompt aliases.
- Release evidence supports the claimed `LOCAL`, `V1`, `V2`, or `V3` behavior.
