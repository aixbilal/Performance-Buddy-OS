# 29.14 — Checkpoints and Resumability

## Purpose

Resume long or interrupted runs without repeating side effects, using stale permissions, or treating partial model output as trusted state.

## Checkpoint contents

Store run/application/state/schema versions, completed step IDs, typed artifact references/hashes, source revisions, permission/consent references, budgets consumed, model/tool versions, idempotency keys, pending step, expiry, and encrypted/redacted storage metadata. Avoid raw sensitive context unless necessary and explicitly governed.

## Resume rules

Verify checkpoint integrity and compatibility; reacquire authorization/consent; check source freshness, model/tool availability, budgets, leases, and user cancellation; migrate only through tested paths; then resume from the last durable side-effect boundary. Never replay uncertain writes. Stale proposals return to validation/approval.

Users can inspect/cancel resumable runs. Expired, revoked, incompatible, or corrupt checkpoints are safely discarded or archived as redacted diagnostics.

## Acceptance criteria

- Crash tests at every transition produce no duplicate writes or skipped validation.
- Checkpoint deletion/revocation removes eligible sensitive artifacts.
- Resume works across supported application/schema updates or fails clearly.
