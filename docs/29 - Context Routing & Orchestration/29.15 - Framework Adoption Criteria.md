# 29.15 — Framework Adoption Criteria

## Decision principle

Do not adopt an orchestration framework because it is popular or a feature may eventually need it. Adopt only after native orchestration exposes measured, recurring requirements that a framework satisfies with acceptable risk.

## Evaluation dimensions

Typed state/state-machine fit; durable checkpoints; cancellation; retries/idempotency; human approval; streaming; tool controls; observability; testing/replay; migration/versioning; local/offline compatibility; provider neutrality; security/supply chain; data residency; performance; maintenance health; license; documentation; debugging; vendor lock-in; dependency size; and exit strategy.

## Required comparison

Use representative V1, V2 scheduled, V3 standard, and approved deep-specialist workflows. Compare native baseline, candidate framework, and simplest alternative on correctness, failure recovery, developer effort, latency, cost, operability, and migration burden. Security review and prototype evidence precede commitment.

## Acceptance criteria

- A documented decision records requirements, weighted evidence, rejected options, risks, and rollback/exit plan.
- Domain/application contracts remain framework-neutral.
- Adoption cannot weaken permissions, audit, validation, approval, or offline CORE.
