# 29.10 — Native Orchestration

## Decision

The default implementation is a small provider-neutral orchestration service using ordinary application code, typed state, explicit transitions, registered tools, persistence adapters, and observability. Exact libraries are implementation choices, not documentation authority.

## Responsibilities

Validate application manifests; route intent/model; build context; enforce budgets; invoke adapters/tools; validate outputs; manage state/checkpoints; apply cancellation/timeouts/retries; call Phase 23; request approval; record redacted telemetry; and clean up.

## Advantages and limits

Native control minimizes dependencies, preserves debugging clarity, and fits simple V1/V2/standard V3 flows. It must still implement durable state, concurrency, idempotency, migrations, and recovery correctly. Complexity is measured from real requirements rather than assumed away.

Framework-neutral interfaces prevent domain logic, prompts, schemas, and checkpoints from depending on an orchestration vendor.

## Acceptance criteria

- Contract and chaos tests demonstrate state safety, cancellation, recovery, and observability.
- A deterministic test adapter runs workflows without external models.
- Framework adoption remains optional and does not require domain rewrites.
