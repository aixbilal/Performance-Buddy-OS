# 29.02 — Model Router

## Purpose

Select an approved inference adapter/configuration that satisfies an application's declared requirements and current user policy.

## Decision inputs

Application capability, task type, modality, context/output limits, structured-output/tool requirements, privacy locality, data categories, user preference, provider consent, hardware readiness, measured quality, latency, cost, availability, rate limits, and fallback policy.

## Rules

Filter by hard privacy, capability, and evaluation gates before optimizing latency or cost. `LOCAL` and `CLOUD` describe execution location, not intelligence quality. Never silently switch to remote processing, a weaker schema guarantee, unapproved model, or higher reasoning mode. Record selected provider/runtime, model/version, adapter, parameters, reason, and rejected constraints.

Model routing occurs before content transfer. A selection is revalidated if data scope, mode, provider state, or application version changes.

## Acceptance criteria

- Identical eligible manifests produce explainable, policy-compliant selections.
- Outage and quota tests never weaken consent, privacy, or capability requirements.
- No eligible model yields a clear fallback rather than fabricated output.
