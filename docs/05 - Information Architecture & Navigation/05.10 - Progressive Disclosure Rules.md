# Progressive Disclosure Rules

## Purpose

Control when detail, advanced capability, evidence, and system complexity appear so common work stays calm and understandable.

## Levels

1. **Essential:** current state, primary action, critical constraint/error.
2. **Supporting:** reasons, relevant relationships, small set of alternatives.
3. **Detailed:** evidence, history, formulas, metadata, uncertainty.
4. **Advanced:** configuration, diagnostics, permissions, migrations, model/provider detail.

## Rules

- Do not hide safety, destructive consequences, approval requirements, or critical uncertainty.
- Do not force advanced users through unnecessary steps for safe frequent actions.
- Preserve discoverability with clear labels, help text, and consistent expansion patterns.
- Remember disclosure preference only when it does not conceal newly critical state.
- Use domain-appropriate summaries; do not reduce complex evidence to misleading badges.
- AI reasoning summaries show enough evidence and constraint information for an informed approval, with deeper trace available.

## Capability disclosure

CORE surfaces remain primary. Unavailable LOCAL/V1–V3, CLOUD, and MOBILE features should not crowd navigation. When shown, they are labeled as optional, unavailable, planned, or permission-required—not implied to work.

## Error and empty states

Give the immediate explanation and safe recovery first; technical detail expands on demand. Empty states distinguish “no records,” “not permitted,” “not indexed,” “offline optional service,” and “insufficient evidence.”

## Accessibility

Disclosure controls are keyboard operable, expose state to assistive technology, retain focus predictably, and never rely solely on hover.

## Acceptance criteria

Common workflows show only necessary complexity while consequential decisions retain sufficient context, explanation, and recovery information.
