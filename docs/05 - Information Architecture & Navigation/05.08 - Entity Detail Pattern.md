# Entity Detail Pattern

## Purpose

Define a consistent information pattern for viewing and acting on domain entities without forcing identical screens.

## Pattern

An entity detail view may contain:

1. **Identity:** title, type, owner domain, status, capability/source badges.
2. **Summary:** current meaningful state and primary next action.
3. **Relationships:** parent/child and cross-domain references.
4. **Evidence/activity:** chronological or categorized history with provenance.
5. **Insights:** deterministic metrics and labeled AI interpretations.
6. **Actions:** owner-validated commands with permissions and confirmation.
7. **Metadata:** IDs, dates, source/version, privacy, sync/index state where relevant.

Not every entity needs every section. Domain meaning determines emphasis.

## State separation

Current state, historical record, projection, inference, and recommendation must look and read differently. Draft/unsaved edits are distinct from confirmed records. AI proposals display before/after effects and approval status.

## Editing

The owner domain validates edits. Inline editing is used only when context and recovery remain clear. Consequential or multi-field changes use a focused workflow with cancel/undo behavior.

## Privacy

Sensitive fields can be hidden, summarized, or excluded by permission. Entity existence and relationship links may also require protection. Audit metadata should not expose private content unnecessarily.

## Acceptance criteria

Different domain details feel structurally familiar while preserving specialist rules, actions are attributable, and users can inspect provenance and explanation without mandatory clutter.
