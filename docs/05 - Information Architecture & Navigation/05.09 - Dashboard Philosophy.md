# Dashboard Philosophy

## Purpose

Define dashboards as decision-support views rather than decorative metric collections or alternate sources of truth.

## Principle

A dashboard should help answer a bounded question and support a next step. It is not valuable because it contains many cards, charts, streaks, or real-time numbers.

## Dashboard types

- **Operational:** What needs attention now? Example: Today.
- **Domain:** What is the current state of this area? Example: academics.
- **Review:** What changed over a selected period and why?
- **System:** Is data, backup, sync, indexing, or an integration healthy?

## Content rules

Each component states its metric/record owner, time window, data coverage, freshness, and interaction. Derived metrics link to explanation and inputs. Recommendations link to evidence and approval. Empty and insufficient-data states teach rather than fabricate.

## Anti-patterns

- One universal performance score.
- Money or spiritual practice folded into a moral ranking.
- Color-only status or alarmist language.
- Charts without a decision purpose.
- Duplicated domain editors inside dashboard cards.
- Future V2/V3 insights shown as if CORE already supports them.

## Personalization

Users may arrange or hide nonessential modules, but cannot hide critical conflicts or weaken permissions through layout. Defaults favor calm hierarchy and limited high-value signals.

## Acceptance criteria

Every dashboard has a declared question, supports drill-down to canonical owners, remains useful offline at CORE, and reduces rather than increases cognitive load.
