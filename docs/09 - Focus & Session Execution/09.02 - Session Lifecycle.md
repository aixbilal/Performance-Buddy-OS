# Session Lifecycle

## Canonical states

`Draft → Active → Paused/Interrupted → Active → Completing → Saved`

Exceptional states are `Cancelled`, `Discarded`, and `Failed to Save`. A recoverable local draft exists before or immediately after activation so a crash does not erase the session.

## Transition rules

| From | Event | To | Required behavior |
|---|---|---|---|
| Draft | Start | Active | Record start time and immutable origin reference |
| Active | Pause | Paused | Stop active-time accumulation; retain wall-clock history |
| Active/Paused | Interruption | Interrupted | Record reason only when the user chooses |
| Paused/Interrupted | Resume | Active | Append a new active interval |
| Active/Paused | Finish | Completing | Request outcome and proportionate evidence |
| Completing | Confirm | Saved | Persist actual record and reconcile linked plan |
| Any unsaved | Storage failure | Failed to Save | Retain draft and offer safe retry |

## Record integrity

The session stores origin, linked entities, planned target if any, interval history, notes, outcome, evidence references, and timestamps. Edits after saving create an auditable revision; they do not silently alter the original plan or prior analytics input.

## Recovery and idempotency

Retries use a stable session identifier so repeated save requests cannot create duplicates. On restart, the system offers to resume, complete, or discard a recovered draft. Discard requires confirmation when meaningful notes or time intervals exist.

## Boundary

Lifecycle logic is deterministic `CORE`. Intelligence can propose completion text or classify a note, but state transitions remain rule-validated and user-confirmed.
