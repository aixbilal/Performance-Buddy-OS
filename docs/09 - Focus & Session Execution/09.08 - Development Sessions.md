# Development Sessions

## Purpose

Development sessions cover coding, full-stack study, AI engineering, project work, debugging, and technical practice. The Development domain owns project and learning-path semantics; Phase 09 owns execution capture.

## Suggested context

A session may link a project, repository, issue, feature, technology, learning-path unit, or practice objective. An intended outcome should describe a testable change or learning result, not merely “code for an hour.”

## Evidence

Examples include a local diff, tests run with results, a commit reference, a deployed preview, a reproduced defect, design notes, or a written explanation. A commit is useful provenance but is not automatically proof of correctness. Secrets, credentials, private source, and command output must not be copied to cloud intelligence without explicit authorization.

## Completion

The closing record separates implementation status, verification status, blockers, and next action. “Implemented but unverified” is not equivalent to complete. Long-running commands and background services must be represented honestly rather than inflating active focus time.

## Assistance boundary

AI assistance is labeled by capability and recorded when relevant. AI-off practice can disable generation while preserving normal local execution tools and manual notes.
