# Feature Dependency Graph

## Core graph

```text
Source truth + capability registry
        ↓
Canonical schemas + IDs + revisions + migrations
        ↓
Repositories + application commands + deterministic rules
        ↓
Desktop shell + Today + sessions/trackers + domain vertical slices
        ↓
Events/analytics + backup/export/recovery + security/QA/release
        ↓
LOCAL runtime ─→ V1 assistant ─→ V2 historical coach ─→ V3 cross-domain intelligence
        ↓                │
Optional CLOUD sync/services ─→ optional MOBILE companion
```

## Edge rules

An edge means the downstream feature requires a stable tested contract, not that the upstream implementation must be feature-complete. Domain vertical slices may progress in parallel after shared foundations stabilize. CLOUD can support V1 providers without being required for local V1; MOBILE depends on approved transfer/sync but not V3.

Each feature record names hard dependencies, optional enablers, blockers, compatibility, fallback, and proof. Circular dependencies trigger redesign. UI cannot be declared done before persistence/rules/testing/recovery contracts exist.

## Acceptance criteria

- Every planned feature traces to required schemas, commands, permissions, tests, and recovery.
- Critical path and parallelizable work are visible.
- Optional capability edges cannot become hidden CORE dependencies.
