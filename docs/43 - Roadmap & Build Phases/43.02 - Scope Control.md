# Scope Control

## Scope unit

Every candidate feature records stable ID, problem, target user outcome, domain owner, capability, status, dependencies, non-goals, offline behavior, data/permissions, deterministic boundary, approval behavior, acceptance tests, effort range, risks, fallback, and deferral cost.

## Selection rules

Prioritize required foundations, daily user value, risk reduction, architectural learning, and end-to-end completeness. Prefer a narrow finished workflow over many disconnected screens. Feature count, novelty, code volume, and “AI can generate it quickly” are not priority evidence.

New scope enters an intake list and receives impact analysis against the frozen baseline, source authority, schemas, UX, security, testing, recovery, and roadmap. Structural documentation changes follow Phase 00; roadmap placement alone cannot approve them.

Use explicit in-scope, out-of-scope, and deferred lists per stage. Scope changes identify displaced work and revised acceptance evidence. Stop or simplify work whose complexity exceeds demonstrated value.

## Acceptance criteria

- Every active item satisfies Definition of Ready.
- Unplanned requests cannot enter a sprint/build slice without disposition.
- Scope review detects architecture drift and optional features blocking CORE.
