# Deferred Features

## Purpose

Deferral protects delivery and learning by recording worthwhile ideas without treating them as commitments. Every entry is `FUTURE` until approved promotion.

## Register fields

Record ID, title, user problem, proposed domain/capability, reason deferred, prerequisites, data/permission/security impact, likely complexity, alternatives, evidence, owner, decision date, review trigger, and status. Do not collect credentials, reserve schemas, or create provider dependence for deferred work.

## Typical deferred categories

Potential examples include full mobile parity, autonomous actions, social/community features, institutional multi-user administration, public APIs, broad wearable/banking integrations, advanced health interpretation, real-time collaboration, custom plugin marketplace, complex cloud orchestration, and speculative V3 specialists. Inclusion here is not endorsement.

Reconsider only when the user problem persists, lower dependencies are stable, simpler alternatives are insufficient, and capability promotion evidence can be planned. Rejected ideas retain rationale to prevent repeated ungrounded reintroduction.

## Acceptance criteria

- Deferred items are absent from committed scope, UI claims, and release promises.
- Each item has a reason and objective review trigger.
- Promotion requires Definition of Ready and Phase 02 approval; it cannot occur by renaming status.
