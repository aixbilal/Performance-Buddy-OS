# Cross-Domain Interaction Map

## Purpose

Define approved cross-domain information flows, validation points, and prohibited coupling.

## Interaction matrix

| Producer | Consumer | Approved purpose |
|---|---|---|
| Academic | Performance | Deadlines, attendance/exposure, study demand, risk |
| Knowledge | Academic/Development | Topic evidence and confidence |
| Fitness/Recovery | Performance | Feasible load and recovery constraints |
| Routine/Spiritual | Performance | Fixed/flexible routine commitments |
| Money | Analytics | Domain-specific spending review only |
| All domains | Analytics | Permissioned facts for derived metrics |
| Analytics | Intelligence | Trends and evidence windows with provenance |
| Intelligence | Domain/Performance | Proposals, never direct authoritative facts |
| Platform | All domains | Storage, permissions, offline and delivery services |

## Interaction pattern

```text
OWNER RECORD → PERMISSION FILTER → DERIVED CONTEXT
             → RULE VALIDATION → PROPOSAL → HUMAN APPROVAL
             → OWNER COMMAND → AUDITABLE RESULT
```

Not every interaction uses AI. CORE planning and analytics should use deterministic contracts first.

## Constraints

Cross-domain priority does not erase protected constraints. Missing data remains unknown. Sensitive spiritual, reflection, fitness, academic, and financial data is not shared merely because it could improve a model. Aggregate metrics must remain interpretable from their domain components.

## Failure behavior

If a producer or optional integration is unavailable, consumers show stale/unavailable context and continue where safe. They do not fabricate defaults. Failed proposals leave owner data unchanged.

## Prohibited coupling

No direct database-table dependency as the domain contract; no AI-written cross-domain state without approval; no universal score; no cloud-only interaction for CORE; no event cascade that obscures why a record changed.
