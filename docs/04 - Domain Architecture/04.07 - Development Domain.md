# Development Domain

## Purpose

Define technical-learning paths, deliberate practice, projects, and evidence of independent software-development capability.

## Responsibilities

Development owns chained technical learning paths, modules, sessions, learn-practice-build cycles, project milestones, development notes, skill evidence, AI-assisted coding boundaries, AI-off practice, debugging practice, architecture practice, workload, and priority relative to academics.

## Core concepts

Learning path, prerequisite, module, practice task, build task, project, milestone, skill evidence, review, and load state. Framework/tool choices are not domain facts until approved through Phase 44 decisions.

## Interactions

Knowledge supplies sources, notes, topics, and learning evidence. Performance schedules development actions. Academic context can change allocation. Analytics measures path progress and friction. Intelligence may explain, review, or propose next practice while preserving human understanding.

## Invariants

Course/tutorial completion is not proof of skill. Useful evidence includes independent implementation, tests, debugging, explanation, refactoring, and retained understanding. AI-generated code requires review and validation. AI-off practice remains configurable and meaningful.

## Boundaries

Development does not own product platform technology decisions merely because they are learning opportunities. It cannot sacrifice protected sleep or bypass academic risk rules. It is a core long-term domain, not automatically secondary.

## Acceptance criteria

Paths show prerequisites and evidence, project work is traceable to learning objectives, and assistance increases rather than replaces capability.
