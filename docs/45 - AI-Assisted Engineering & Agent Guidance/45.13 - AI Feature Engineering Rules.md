# AI Feature Engineering Rules

## Architecture rule

AI features implement Phase 24's application model: versioned instructions, bounded context, structured outputs, controlled tools, explicit memory, deterministic rules, permissions, provenance, and evaluation. Provider SDKs remain behind approved adapters. Domain truth never lives only in a prompt.

## Engineering requirements

- Assign an approved `LOCAL`, `V1`, `V2`, or `V3` capability and define non-goals.
- Minimize context by purpose and permission zone; exclude `NEVER_AI` data and disclose cloud exposure.
- Treat retrieved content and tool output as untrusted; defend against prompt injection and provenance loss.
- Validate schemas, identifiers, target revisions, permissions, constraints, and calculations deterministically.
- Separate read, proposal, approval, commit, and audit stages. A model cannot approve its own write.
- Make tools least-privilege, idempotent where possible, bounded, cancelable, and safe under retry or stale context.
- Provide abstention, uncertainty, citations where required, provider failure handling, and a usable lower-level fallback.
- Version model alias/resolution, prompts, schemas, tools, policies, datasets, and evaluation results.
- Measure quality, safety, privacy, latency, and cost through Phase 24 and Phase 40 gates before promotion.

## Acceptance criteria

- Provider or network failure cannot corrupt CORE state.
- Every consequential recommendation is explainable and independently validated.
- Approval and permission paths cannot be bypassed by background, retry, or alternate UI paths.
- Release evidence supports the exact capability claimed.
