# Documentation Update Requirement

## Rule

Documentation is part of the change, not a later cleanup task. Implementation must not knowingly diverge from approved behavior. Updates go to the owning document; they do not duplicate authority in convenient nearby files.

## Change impact checklist

Update applicable requirements, contracts, schemas, migrations, APIs/events, permissions, offline/failure/recovery behavior, tests/evaluations, operations, ADRs, capability registry/status, and release notes. Record material source-of-truth changes through Phase 00 change control.

The frozen blueprint defines paths and names. Agents may edit content within authorized scope, but may not add, remove, rename, reorder, merge, or split baseline documents without an approved baseline revision. Historical decisions remain in the decision log or ADR record rather than being silently rewritten.

Code comments explain local intent or constraints and do not replace product documentation. Generated documentation must be checked against the actual implementation and source authority. Links use stable repository paths and are validated after moves approved through change control.

## Completion evidence

The change review states which documentation was assessed, what was updated, and why unaffected authoritative documents required no update. If documentation cannot be updated safely because a decision is unresolved, the change is not done.

## Acceptance criteria

- Requirement, code, schema, and test references remain traceable.
- No duplicate document becomes an accidental source of truth.
- Baseline structure changes only through approved revision policy.
- Documentation and implementation describe the same released behavior.
