# Database Engineering Rules

## Authority

Phase 32 owns canonical data meaning, Phase 33 owns local authority, Phase 34 owns optional synchronization, and Phase 39 owns backup and recovery. Application services—not UI components, prompts, or model output—mediate domain writes.

## Required rules

- Use stable identifiers, explicit revisions, timestamps with defined semantics, provenance, and database-enforced constraints where possible.
- Validate domain invariants before commit and use transactions for atomic state changes.
- Parameterize queries; bound result sets; define indexes from measured access patterns.
- Make retries and background work idempotent. Record conflict and audit information without storing prohibited sensitive content.
- Every schema change has a versioned forward migration, compatibility analysis, representative fixtures, failure behavior, backup expectation, and restore/rollback strategy.
- Never edit production-like databases manually to conceal a migration defect. Never destroy data to simplify a schema change.
- Test empty, boundary, malformed, duplicate, concurrent, interrupted, upgrade, downgrade/rollback where supported, backup, and restore cases.
- Preserve soft delete and restoration semantics according to Phase 32.

AI-generated SQL and migrations are untrusted until reviewed against the canonical schema and exercised on disposable data. Sensitive rows must not be sent to an external model for debugging.

## Acceptance criteria

- Constraints and tests protect canonical invariants.
- Migrations are repeatable, observable, and recovery-tested.
- Offline local authority remains correct without cloud or AI.
- Data loss, silent truncation, and untracked semantic changes block release.
