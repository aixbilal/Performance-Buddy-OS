# Code Understanding Requirements

## Understanding standard

Consequential code is not accepted solely because it was generated, compiles, or passes a narrow test. The responsible human must be able to explain its purpose, owning requirement, inputs and outputs, state changes, trust boundaries, error paths, tests, and operational consequences at a depth proportional to risk.

## Required evidence

For material work, preserve:

- a map from requirement to modules and contracts;
- data flow and authority, including validation and persistence boundaries;
- invariants, algorithms, assumptions, complexity, and concurrency behavior;
- permission, privacy, security, offline, recovery, and migration behavior;
- dependency purpose and verified API/version assumptions;
- test rationale, observed failures, and why the fix addresses the root cause.

The human should be able to navigate to the relevant code, predict representative behavior, modify a bounded part, and diagnose a failure without asking an AI to regenerate the feature. This does not require memorizing syntax; it requires ownership of meaning and consequences.

## Check methods

Use explain-back, diagramming, trace-through, test prediction, AI-off debugging, small refactoring, or code review questions. Preserve the original independent attempt when it forms learning evidence, consistent with Phase 18.

## Acceptance criteria

- Consequential paths have an explainable requirement-to-code trace.
- The owner can distinguish domain rules from orchestration and infrastructure.
- Generated code with unexplained behavior is revised, isolated, or rejected.
- Learning evidence never equates AI output with independent mastery.
