# Architecture Before Code

## Rule

Implementation begins only after the change is ready under Phase 43. Architecture work must be proportional: a small fix may need a short boundary note, while a schema, security, synchronization, platform, or AI change may require research and an ADR.

## Pre-code brief

Before editing, identify:

- user outcome, scope, non-goals, capability label, and owning documents;
- affected domains, entities, invariants, interfaces, and source authority;
- deterministic versus probabilistic responsibilities;
- permissions, privacy zones, threats, approval, and audit needs;
- offline, degraded, failure, retry, undo, backup, and recovery behavior;
- compatibility, schema migration, performance, and accessibility impact;
- alternatives, selected approach, unresolved facts, and validation plan.

Technical selections belong to Phase 44 research and approved ADRs. An agent may compare options, but it may not silently select a framework, provider, database, encryption design, or orchestration system. Unverified external facts are marked `RESEARCH REQUIRED`.

## Change discipline

Inspect existing code and documentation before proposing new structures. Reuse owned contracts where they fit; do not duplicate domain truth in UI, prompts, adapters, or tests. If implementation exposes a missing or conflicting architecture decision, stop that portion and record the conflict instead of encoding an accidental decision.

## Acceptance criteria

- The pre-code brief traces each consequential choice to authority or an approved decision.
- Architecture depth matches risk and change size.
- Tests are derived from invariants and failure paths before acceptance.
- Code does not establish an unapproved architecture by default.
