# Architecture Drift Detection

## Definition

Architecture drift is an implementation, configuration, schema, dependency, prompt, or document that contradicts approved boundaries or establishes an unapproved decision. Not every difference is drift; an approved ADR may intentionally evolve an earlier provisional design.

## Detection checks

At review and release gates, compare the change with:

- locked paths, terminology, source authority, and capability ownership;
- domain/application/infrastructure boundaries and canonical data ownership;
- deterministic versus AI responsibilities and approval contracts;
- permission zones, secret rules, data exposure, provenance, and audit behavior;
- offline authority, optional cloud removal, failure, recovery, and compatibility;
- approved frameworks, dependencies, APIs, schemas, migrations, and ADRs;
- test/evaluation coverage and claimed completion status.

Automate checks for manifests, forbidden imports/dependencies, dependency direction, schema versions, capability labels, links, contracts, and policy tests where practical. Human review remains necessary for semantic drift.

## Response

Record evidence, affected owners, user/data/risk impact, cause, and disposition. Correct accidental drift in scope and rerun validation. Intentional change requires the appropriate research, ADR, source update, migration, and approval before implementation is accepted. Do not alter documentation merely to legitimize accidental code.

## Acceptance criteria

- Drift checks run at architectural boundaries and before release.
- Each finding is fixed, formally approved, deferred with owner/risk, or blocks completion.
- Capability inflation and silent optional-service dependencies are detected.
- Architecture and implementation converge through evidence, not retrospective rewriting.
