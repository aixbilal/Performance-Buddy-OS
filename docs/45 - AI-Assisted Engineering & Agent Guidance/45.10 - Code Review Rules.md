# Code Review Rules

## Review objective

Review protects product meaning, data, users, and maintainability. It evaluates the actual diff in its execution context—not only style, isolated snippets, or the author's explanation.

## Required review order

1. Confirm scope, authority, acceptance criteria, capability, and architectural ownership.
2. Check correctness, invariants, state transitions, calculations, time/locale behavior, concurrency, and error handling.
3. Check authorization, privacy zones, secrets, injection, dependency/supply-chain risk, and safe logging.
4. Check schema constraints, migrations, compatibility, offline behavior, sync, backup, undo, and recovery.
5. Check UX states, accessibility, performance, observability, and explainability.
6. Check test adequacy, determinism, fixtures, failure cases, and regression coverage.
7. Check documentation, ADR, and capability/status updates.

Findings identify exact evidence, impact, reproducible scenario, severity, and smallest safe correction. Distinguish blocking defects from suggestions. Avoid speculative complaints and formatting noise already covered by tools.

AI review is supplementary. High-impact security, migration, permissions, calculations, releases, and AI evaluation require accountable human review. The author must not mark unresolved findings fixed without evidence.

## Acceptance criteria

- Review covers requirement compliance and failure paths, not only happy-path syntax.
- Blocking findings map to risk and evidence.
- Resolutions include relevant regression checks.
- Approval never substitutes for required automated or specialist gates.
