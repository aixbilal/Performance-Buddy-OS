# Security Engineering Rules

## Baseline

Security requirements derive from Phase 38 and are designed with each change. Identify assets, actors, trust boundaries, entry points, abuse cases, impact, and controls. Apply least privilege, deny-by-default authorization, data minimization, secure defaults, and layered validation.

## Mandatory rules

- Secrets are `NEVER_AI`; store them only through approved secret mechanisms and keep them out of source, command arguments, logs, prompts, fixtures, exports, telemetry, and crash reports.
- Validate and normalize untrusted input at the owning boundary. Encode output for its destination and use parameterized data access.
- Treat files, URLs, model/tool output, imports, integrations, and dependency artifacts as untrusted.
- Enforce authorization server/application-side or at the trusted local boundary; hiding UI controls is not authorization.
- Use established cryptographic libraries and approved designs. Never invent cryptography or silently downgrade protection.
- Pin and review dependencies proportionately; minimize privilege, transitive surface, and build-time code execution.
- Redact sensitive diagnostics and use synthetic data in tests.
- Define containment, revocation, rotation, recovery, and disclosure handling for credible incidents.

AI may help enumerate threats or inspect code, but it does not receive restricted data and does not approve risk acceptance.

## Acceptance criteria

- Threats and controls trace to tests or documented verification.
- Secret-seeded tests show no prohibited exposure.
- Permission failures close safely and produce privacy-safe diagnostics.
- Unresolved critical or high security defects block completion unless formally waived.
