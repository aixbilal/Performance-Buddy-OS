# Boolean Trackers

## Purpose

A Boolean tracker records whether one clearly defined action or condition was completed for an occurrence. It is appropriate only when a truthful yes/no completion claim is meaningful.

## Data contract

The record stores `true` only for confirmed completion. `false` may represent an explicit `Skipped` or incomplete outcome according to owner rules; absence remains `Unknown`. State and Boolean value must not contradict each other. Optional evidence, note, source, and completion time remain separate fields.

## Rules

- Never default an overdue missing record to `false`.
- Do not use Boolean tracking where quantity, quality, subtasks, or reflection matters.
- Automatic `true` requires an authoritative deterministic event.
- Reversing a value creates a revision and recomputes dependents.
- A simple user attestation is sufficient only when the owner domain permits it.

## Examples and boundaries

Suitable examples include “medication logged” only if health scope permits, “daily review completed,” or “backup verified.” Hydration volume should be numeric or count-based; prayer sets may require multi-check semantics; study mastery cannot be reduced to a Boolean timer result.

## Acceptance criteria

Unknown and false remain distinct, evidence is proportionate, history is auditable, and domain-specific meaning is never invented by the generic engine.
